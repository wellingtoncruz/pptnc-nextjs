UX Design Specification - IAra

Author: Wellington Date: 2026-01-24

Executive Summary

Project Vision

O IAra é uma plataforma web de gestão do pipeline de publicação de podcast com automação via LLM. A interface é uma SPA desktop-first focada em produtividade operacional para um produtor não técnico que trabalha em sessões noturnas. O fluxo core é: Detectar novos vídeos → Processar metadados → Revisar → Publicar, um vídeo por vez. A metáfora visual é uma esteira de produção (entrada → processamento → saída), não um dashboard genérico de vídeos.

Target Users

Carlos (Produtor) — Usuário Principal:

  • Não técnico, experiência com YouTube Studio e redes sociais
  • Trabalha à noite com tempo limitado
  • Gerencia ~22 vídeos/semana em sessões parciais
  • Precisa de interface zero-friction, óbvia sem explicação
  • Modelo mental: vem do YouTube Studio (lista + edição inline), mas IAra é ferramenta de processamento, não gerenciador de vídeos

Wellington (Admin) — Usuário Secundário (Phase 2 Growth):

  • Técnico, gerencia prompts e configurações
  • Acessa seção "Configurações" para CRUD de tipos/prompts
  • Consulta métricas de reprocessamento

Key Design Challenges

  1. Usuário não técnico operando sistema complexo — Abstrair toda a complexidade de LLMs, APIs e configurações. Cada ação óbvia sem explicação.
  2. Feedback de processamento assíncrono (30-120s) — Comunicar progresso via SSE de forma reconfortante, sem ansiedade.
  3. Compliance sem bloqueio — Alertas com tom suave (amber-200, ícones informativos). Linguagem "dá uma olhada nisso", não "PERIGO!".
  4. Densidade de informação por vídeo — Título, descrição, tags, capítulos, compliance em uma tela sem sobrecarregar.
  5. Diferenciação do YouTube Studio — Comunicar que é ferramenta de processamento, não dashboard de analytics/gerenciamento.

Design Opportunities

  1. Fluxo "one thing at a time" — Um vídeo por vez em foco, com sidebar/breadcrumb mínimo de progresso ("X de Y processados").
  2. Sensação de progresso — Indicadores visuais motivam nas sessões noturnas. Lista diminuindo = produtividade tangível.
  3. SSE como "mágica acontecendo" — Metadados aparecendo campo a campo ao invés de spinner genérico.
  4. Tabs/filtros por status — Novos | Em Processamento | Prontos | Enviados. shadcn-native, sem drag desnecessário. Fluxo visual de esteira.
  5. Consistência com Portal PPTNC — shadcn/ui + Tailwind, mesma linguagem visual do ecossistema.

Design Foundations

Visual:

  • Look and feel idêntico ao Portal PPTNC
  • Dark mode only (sem toggle — classe dark fixa no <html>)
  • shadcn/ui components + Tailwind CSS
  • Desktop-first (responsive básico para tablet, mobile não prioridade)
  • Componentes theme-aware internamente, app theme-fixed em dark

Legibilidade em Dark Mode:

  • Textos longos em cinza claro (não branco puro) — reduz fadiga visual
  • Contraste adequado para leitura prolongada em sessões noturnas
  • Alertas de compliance em tons suaves (amber-200, não yellow-500)

Core User Experience

Defining Experience

Core Loop: Selecionar vídeo → Processar → Revisar → Enviar

Este é o loop que Carlos repete ~22x por semana. Toda a UX da IAra existe para tornar esse loop o mais fluido possível. A interface deve permitir que Carlos entre, processe o que der, e saia — sem cerimônia, sem atrito, sem surpresas.

Ação mais frequente: Clicar "Processar" em um vídeo e revisar o resultado. Ação mais crítica: Revisar metadados e decidir "enviar" ou "reprocessar". Ação que deve ser effortless: Tudo que não é decisão humana (detecção, classificação, seleção de prompts, persistência).

Effortless Interactions

Zero pensamento necessário:

  • Verificar novos vídeos — Um botão, resultado em segundos
  • Classificação por tipo — Automática por duração, sem decisão do produtor
  • Seleção de prompts — Automática por tipo de vídeo (N:N)
  • Persistência — Rascunhos salvos automaticamente, sem "Save"
  • Envio para YouTube — Um clique por vídeo, confirmação persistente (mudança de status visual, não toast temporário)

Automático (sem intervenção):

  • Compliance check executado junto com metadados
  • Status do vídeo atualizado automaticamente
  • Reconexão SSE se stream cair

Estados de falha claros:

  • Falha no envio → Vídeo volta para "Pronto" com indicação "falha no envio, tente novamente" — nunca fica em limbo

Experience Principles

  1. "One click, immediate feedback" — Cada ação do produtor gera resposta visual imediata (nem que seja "processando..."). O resultado chega quando pronto.
  2. "Mostre, não explique" — Interface auto-explicativa. Se precisa de tooltip, está complexo demais.
  3. "Progresso, não perfeição" — O produtor avança vídeo a vídeo. Rascunhos existem para isso. Nenhum vídeo precisa ser perfeito agora.
  4. "A máquina trabalha, você decide" — LLM processa, compliance alerta, mas a decisão final é sempre do produtor.
  5. "Nada se perde" — Rascunhos persistem, estado preservado, crash não apaga trabalho. Falha de envio retorna ao estado anterior, nunca limbo.

Emotional Design Principles

  1. "Ambiente noturno" — A interface deve parecer um espaço de trabalho noturno calmo, não um cockpit cheio de luzes.
  2. "Micro-recompensas" — Cada vídeo processado e enviado é uma pequena vitória visual. Acumular vitórias motiva.
  3. "Informar, não alarmar" — Compliance e erros comunicam com neutralidade e clareza, nunca com urgência ou medo.
  4. "Presença silenciosa" — O sistema trabalha em background. O produtor só interage quando há decisão humana a tomar.
  5. "Tempo respeitado" — Nenhuma interação desperdiça tempo do produtor. Se o sistema pode decidir sozinho, decide.

UX Pattern Analysis & Inspiration

Inspiring Products Analysis

YouTube Studio:

  • Problema que resolve bem: Gestão de conteúdo de vídeo com edição inline direta na lista
  • Padrão de navegação: Lista vertical com metadados visíveis, clique para expandir/editar
  • Força UX: Familiaridade para Carlos — modelo mental já estabelecido
  • Fraqueza UX para IAra: É um gerenciador de conteúdo, não uma ferramenta de processamento. IAra não deve parecer um dashboard de analytics

Linear:

  • Problema que resolve bem: Gestão de tarefas com foco e clareza, sem ruído visual
  • Padrão de navegação: Sidebar mínima + área de trabalho ampla, transições suaves
  • Força UX: Clean, keyboard-friendly, estados claros, sensação de progresso ao completar itens
  • Fraqueza UX para IAra: Complexidade de configuração desnecessária para Carlos (filtros, views, labels)

Anti-Patterns to Avoid

Dashboard com múltiplas listas/tabs de status Sobrecarga cognitiva para Carlos. Vídeos "prontos" e "enviados" não precisam de lista dedicada Inbox única com itens ativos. Enviados viram histórico

Design Inspiration Strategy

Adotar:

  • Modelo mental de inbox (itens chegam, são processados, desaparecem) — de Linear
  • Edição inline/expandida na lista — de YouTube Studio
  • Empty state celebratório — de Linear
  • Dark mode calmo com tipografia espaçada — de Linear

Adaptar:

  • Lista do YouTube Studio → remover conceito de "gerenciador permanente". Na IAra, itens completados saem da vista
  • Keyboard shortcuts do Linear → simplificar para produtor não-técnico (apenas atalhos óbvios como Enter, Esc)
  • Thumbnails → opacidade reduzida como âncora visual, não destaque principal

Evitar:

  • Múltiplos tabs/filtros de status (YouTube Studio has too many views)
  • Complexidade de configuração de workspace (Linear power-user features)
  • Qualquer animação que pareça "tech demo" em vez de funcional

Design System Foundation

Design System Choice

shadcn/ui + Tailwind CSS — Sistema temável com componentes headless (Radix UI primitives) e utilidades CSS.

Categoria: Themeable System — balanço entre velocidade de desenvolvimento e flexibilidade visual.

Rationale for Selection

Fator Decisão Motivo
Consistência de ecossistema shadcn/ui compartilhado com Portal PPTNC Mesmos componentes, tokens, padrões — reduz carga cognitiva de manutenção
Velocidade de desenvolvimento Componentes prontos, copy-paste-own Dev solo precisa de produtividade máxima sem sacrificar qualidade
Customização Tailwind utilities + CSS variables Dark mode fixo, tokens customizados, sem override de framework pesado
Acessibilidade Radix UI primitives built-in ARIA patterns nativos sem esforço adicional
Bundle size Tree-shakeable, apenas o que usar SPA precisa de performance — sem framework UI monolítico
Manutenção Componentes locais (não dependência npm) Atualizações sob controle, sem breaking changes surpresa

Implementation Approach

Estrutura de componentes:

src/
  components/
    ui/          ← shadcn/ui base (Button, Card, Input, etc.)
    app/         ← Composições específicas IAra (VideoCard, ProcessingFeed, etc.)

Design tokens via CSS variables (Tailwind):

  • Cores: paleta dark-first com semantic tokens (--background, --foreground, --primary, --muted, etc.)
  • Tipografia: Inter/system-ui, escala de tamanhos consistente
  • Espaçamento: escala Tailwind padrão (4px base)
  • Bordas/Radii: consistente com Portal PPTNC

Componentes core necessários (shadcn/ui):

  • Button, Card, Badge, Input, Textarea — interações primárias
  • Skeleton — loading states durante SSE
  • Alert — compliance warnings (amber tone)
  • ScrollArea — listas de vídeos
  • Separator, Tooltip — organização visual

Customization Strategy

Dark Mode:

  • Classe dark fixa no <html> — sem toggle, sem flash
  • Tokens de cor otimizados para leitura prolongada noturna
  • Backgrounds em zinc/slate-900, textos em zinc-200/300 (não branco puro)
  • Accent colors sutis para ações primárias

Componentes IAra-específicos (não shadcn):

  • VideoCard — thumbnail + metadados + status badge + ação primária
  • ProcessingStream — visualização SSE campo a campo
  • ComplianceAlert — wrapper de Alert com tom amber suave
  • InboxEmptyState — celebração quando inbox vazia
  • OverrideInput — textarea com contexto para instruções adicionais

Princípios de customização:

  1. Usar shadcn/ui as-is sempre que possível (não reinventar)
  2. Compor componentes app-level a partir de primitivos shadcn
  3. Tokens compartilhados com Portal PPTNC via mesma configuração Tailwind
  4. Animações mínimas — apenas transições de estado (opacity, transform), nunca decorativas

Defining Core Experience

The Defining Interaction

"Processar → Ver a mágica → Decidir"

Carlos clica um botão. Em segundos, título, descrição, tags e capítulos começam a aparecer campo a campo na tela. Ele revisa, ajusta se necessário, e envia. Um vídeo resolvido. Próximo.

Se descrever para um amigo: "Eu clico um botão e a IAra escreve tudo pra mim. Eu só confiro e mando."

Se funcionar perfeitamente: O produtor sente que tem um assistente que entende o podcast. Cada clique em "Processar" é uma aposta que quase sempre dá certo.

User Mental Model

De onde Carlos vem:

  • YouTube Studio: lista de vídeos + edição manual de metadados, campo por campo
  • Processo anterior: assistir trechos, pensar em título, escrever descrição, inventar tags — horas por semana

Modelo mental que IAra introduz:

  • Inbox de trabalho — itens chegam, são processados, desaparecem
  • Máquina que escreve — eu não crio conteúdo, eu aprovo conteúdo
  • Esteira de produção — entrada → processamento → saída, um por vez

Onde pode haver confusão:

  • "Cadê meus vídeos enviados?" → Não estão na inbox. São histórico do canal
  • "Posso editar direto?" → Sim, mas o fluxo ideal é: Processar → Revisar → Ajustar (override) → Enviar
  • "O que é override?" → Instruções adicionais para a IA refazer. Ex: "Use um tom mais informal" ou "Mencione o convidado no título"

Success Criteria for Core Experience

Critério Indicador de Sucesso Anti-indicador
Velocidade percebida Primeiro campo aparece em <3s após clique Tela parada por >5s sem feedback
Qualidade do resultado Carlos envia sem editar em >70% dos vídeos Precisa reprocessar >50% das vezes
Confiança no sistema Carlos clica "Processar" sem hesitação Para e pensa "será que vai funcionar?"
Clareza do fluxo Carlos sabe o próximo passo sem pensar Olha a tela e não sabe o que fazer
Sensação de progresso "Já fiz 5 hoje" = satisfação tangível "Quanto falta?" sem resposta visual

Novel vs. Established Patterns

Padrões estabelecidos (familiar para Carlos):

  • Lista vertical de itens (YouTube Studio, email)
  • Campos de formulário para metadados (qualquer CMS)
  • Botões de ação primária proeminentes
  • Status visual por cores/badges

Padrão novel (diferencial IAra):

  • SSE Progressive Reveal — campos aparecem um a um durante geração LLM
    • Não é um padrão que Carlos conhece de outras ferramentas
    • Metáfora: "assistente digitando em tempo real" (familiar de ChatGPT)
    • Reduz ansiedade de espera — algo está acontecendo visivelmente
    • Gera micro-satisfações — cada campo que aparece é um pequeno "uau"

Educação necessária: mínima

  • O SSE progressive reveal é intuitivo — Carlos já viu texto sendo gerado em ChatGPT
  • O conceito de "override" pode precisar de um placeholder sugestivo ("Ex: Use tom mais informal")
  • O modelo inbox se auto-explica: itens estão lá → trabalho neles → desaparecem

Experience Mechanics

1. Initiation — Como o processamento começa:

Estado: Vídeo na inbox (status: novo/rascunho)
Gatilho: Botão "Processar" visível no VideoCard
Contexto: Tipo do vídeo já classificado automaticamente (badge visual)
Ação: Um clique. Sem confirmação modal. Sem configuração prévia.

2. Interaction — O que acontece durante:

Imediato (0-1s): Botão muda para estado "gerando...", área de metadados expande
Progressive (1-120s): Campos aparecem via SSE:
  → Título (primeiro, mais rápido — satisfação imediata)
  → Descrição (aparece em chunks/parágrafos)
  → Tags (aparecem como badges, uma a uma)
  → Capítulos (lista com timestamps)
  → Compliance (badge de status ao final)
Visual: Skeleton → conteúdo real, campo por campo. Smooth transitions.

3. Feedback — Como Carlos sabe que está funcionando:

Durante: Campos preenchendo = sistema trabalhando
Sucesso: Todos os campos preenchidos + compliance badge (verde ou amber)
Compliance amber: Alerta suave inline "Dá uma olhada: [motivo]"
Erro: Mensagem clara + botão "Tentar novamente" (vídeo volta a rascunho)

4. Completion — O que Carlos faz depois:

Revisar: Lê título e descrição (campos editáveis inline)
Decidir:
  → Satisfeito → Clica "Enviar para YouTube" → Item sai da inbox
  → Quase bom → Edita campos diretamente → Envia
  → Precisa retrabalho → Escreve override → Clica "Reprocessar"
  → Compliance preocupa → Lê alerta → Ajusta ou ignora
Próximo: Volta à inbox → Próximo vídeo → Repete loop

5. Retorno (multi-sessão):

Carlos fecha a IAra no meio de uma sessão.
Próxima abertura: Inbox exatamente como deixou.
Rascunhos com metadados parciais: preservados.
Vídeos processados não enviados: continuam na inbox prontos para revisão.
Nenhum trabalho perdido.

Layout (ResizablePanel do shadcn/ui):

  • Baseado em react-resizable-panels — resize nativo, sem CSS grid complexo
  • Sidebar: fixa (w-48), colapsável
  • Lista e Detail: redimensionáveis pelo usuário (drag handle entre colunas)
  • Tamanhos persistidos no localStorage
  • Cada coluna com ScrollArea isolada (scroll independente)

  • Vazio (nenhum vídeo selecionado): empty state "Selecione um vídeo para começar"
  • Carregando (SSE em progresso): skeletons com pulse suave, campos aparecendo progressivamente
  • Preenchido (metadados prontos): campos editáveis, ações disponíveis, micro-resumo no footer
  • Enviado (sucesso): transição → próximo item auto-selecionado

SSE e navegação:

  • Hook de SSE vinculado ao vídeo selecionado
  • Mudar de vídeo durante processamento: SSE anterior continua em background, atualiza lista silenciosamente
  • Detail panel mostra o novo vídeo selecionado sem cancelar streams ativos
  • Múltiplos vídeos podem estar processando simultaneamente (lista reflete status em tempo real)

  • Último vídeo selecionado: localStorage (restaurado ao reabrir)
  • Tamanhos das colunas: localStorage

Flow Optimization Principles

  1. Zero estados de limbo — Cada vídeo está em um estado claro e acionável. Erro retorna a estado anterior, nunca cria estado intermediário
  2. Feedback imediato, resultado quando pronto — Cada clique gera mudança visual instantânea (loading state). O resultado aparece via SSE quando o backend entrega
  3. Auto-continuidade — Pós-envio → próximo item. Pós-erro → retry disponível. Pós-login → onde parou. Nunca dead-end
  4. Edição não-destrutiva — Override é aditivo (instrução ao LLM), edição inline é manual. Ambos preservados. Reprocessar não apaga edições manuais até SSE sobrescrever
  5. Progresso visual acumulado — Contador diminui, lista encurta, empty state celebra. Cada ação move o produtor para "noite produtiva"
