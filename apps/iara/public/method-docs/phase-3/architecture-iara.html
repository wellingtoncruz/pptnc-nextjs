Project Context Analysis

Requirements Overview

Functional Requirements:

9 FRs organizados no escopo MVP:

# Domínio Complexidade Arquitetural
1 Autenticação (GCP IAM + YouTube OAuth) Alta (dual-purpose credentials, consent screen, token refresh)
2 Sincronização de Vídeos (YouTube API read) Média (polling manual, classificação por duração)
3 Processamento LLM (Gemini + SSE) Alta (streaming assíncrono, ReadableStream, timeout, retry)
4 Compliance Check (análise de transcrição) Baixa (subconjunto do processamento LLM)
5 Revisão/Edição de Metadados Média (auto-save com field-level merge, edição inline)
6 Publicação YouTube (API write, dual-mode) Alta (per-video + batch, partial error handling, rollback)
7 Integração Portal Web (Firestore write) Baixa (criação de registro com schema existente)
8 Gestão de Estado (lifecycle por vídeo) Média (state machine com transition function, invariantes)
9 Parametrização (collection podcasts) Média (config-driven execution context, podcastId first-class)

Non-Functional Requirements:

NFR Requisito Impacto Arquitetural
Streaming SSE progressive reveal (30-120s) Route Handler com ReadableStream + contrato de eventos explícito
Persistência Save on blur + save on action Debounce 1.5s + Firestore updateDoc com field-level merge
Cloud Run Timeout para SSE streams Configurar timeout explícito (>5min default)
Middleware Auth check sem buffering de stream Middleware não pode interceptar SSE endpoints
Sessão Persistente, sem relogin frequente Token refresh strategy para OAuth scopes sensíveis
Disponibilidade Tolerante a falhas de APIs externas Circuit breaker, fallback UI, partial batch error handling
Segurança OAuth scopes mínimos, secrets em runtime Secret Manager, server-only credentials, testing mode no MVP
Testabilidade Mock de APIs externas Fixture strategy com snapshot responses, sem sandbox oficial YouTube

Scale & Complexity:

  • Primary domain: Full-stack web app (SPA + API routes + external APIs)
  • Complexity level: Medium
  • Concurrent users: 1-2 (single-tenant MVP)
  • Data volume: ~22 vídeos/semana, ~1000/ano
  • Firestore writes: ~6 field-level merges por vídeo revisado (debounced)
  • Compute: Delegada (Gemini, YouTube) — IAra orquestra

Technical Constraints & Dependencies

  • Monorepo pnpm: apps/iara — compartilha tooling e convenções com portal PPTNC
  • Next.js 15+ premissa: App Router, Route Handlers para SSE (ReadableStream manual)
  • GCP ecosystem: Cloud Run (timeout config), Firestore (field-level merge), IAM, Secret Manager
  • YouTube API quotas: 10.000 units/dia (default) — batch operations devem ser eficientes
  • YouTube OAuth: Consent screen com scopes sensíveis — app em "Testing" mode no MVP (≤100 users)
  • Gemini API: Streaming response, token limits por request, rate limiting
  • Firestore billing: Write-per-field com debounce, evitar writes desnecessários
  • Cloud Run SSE: Timeout default 5min — configurar explicitamente para streams longos

Cross-Cutting Concerns Identified

  1. Authentication & Authorization: Dual-purpose OAuth (app login + YouTube API access), consent screen com scopes sensíveis, token lifecycle, "Testing" mode como constraint MVP
  2. SSE Streaming Contract: Formato de eventos definido como decisão arquitetural (field names, progress format, error format, completion signal) — não delegado ao dev
  3. State Machine: Video status como state machine com transition function explícita — transições inválidas impossíveis por construção, não por validação
  4. Persistence Strategy: Firestore updateDoc com field-level merge, debounce 1.5s, optimistic UI
  5. Batch Publishing: Dual-mode (per-video + multi-select), partial error handling (N de M enviados), sem rollback automático
  6. Config-Driven Context: podcastId como parâmetro first-class em toda query Firestore — isolation by design desde o MVP
  7. Test Strategy: YouTube API sem sandbox — fixture strategy com snapshot responses, mock de EventSource para SSE, state machine invariants como unit tests
  8. Error Handling: Diferenciado por fonte (Gemini timeout vs YouTube quota vs network vs partial batch failure)

Core Architectural Decisions

Decision Priority Analysis

Critical Decisions (Block Implementation):

  • Firestore subcollections (podcasts/{id}/videos/{id})
  • Auth.js v5 com YouTube OAuth scopes
  • SSE hybrid contract (progress/field/complete/error)
  • State machine com transition function

Important Decisions (Shape Architecture):

  • Zustand + URL state
  • Firebase SDK split (client/admin)
  • YouTubeClient + GeminiClient wrappers
  • Cloud Build pipeline
  • Multi-stage Dockerfile

Deferred Decisions (Post-MVP):

  • Staging environment
  • Advanced monitoring (alerts, Sentry)
  • Secret Manager migration
  • Collection group queries (cross-podcast)

Data Architecture

Decisão Escolha Rationale
Collection structure Subcollections: podcasts/{podcastId}/... Isolation by design, white-label ready. Cada podcast é um tenant isolado com deploy independente.
Validation Zod Runtime validation para dados de APIs externas (YouTube, Gemini). Type inference + schema reuse.
Caching Firestore built-in (SDK client cache) Single-user MVP, sem necessidade de cache layer adicional.

White-Label Architecture:

Cada podcast é um tenant isolado com deploy independente:

┌─────────────────────────────────────────────────────────────────┐
│ Cloud Run Deploy: iara-pptnc                                    │
│ PODCAST_ID = 'pptnc' (hardcoded em src/lib/firebase/config.ts) │
│ → podcasts/pptnc/users/{userId}/tokens/oauth                   │
│ → podcasts/pptnc/videos/{videoId}                              │
└─────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────┐
│ Cloud Run Deploy: iara-outro-podcast                            │
│ PODCAST_ID = 'outro-podcast' (hardcoded)                        │
│ → podcasts/outro-podcast/users/{userId}/tokens/oauth           │
│ → podcasts/outro-podcast/videos/{videoId}                      │
└─────────────────────────────────────────────────────────────────┘

  • Mesma base Firestore: isolamento por subcollection
  • Escala horizontal independente: cada Cloud Run service escala separadamente
  • Contas Google separadas: cada tenant tem seu próprio admin com conta Google distinta

Authentication & Security

Decisão Escolha Rationale
OAuth implementation Auth.js v5 (NextAuth) Battle-tested, gerencia token lifecycle, suporta custom scopes YouTube
Token storage Firestore subcollection podcasts/{podcastId}/users/{userId}/tokens/oauth — isolamento por tenant, white-label ready
Route protection Next.js Middleware Gate único para todas as rotas, redireciona se não autenticado

Auth Flow:

1. User acessa /videos → Middleware detecta sem sessão → redirect /api/auth/signin
2. Auth.js inicia OAuth flow com Google (scopes: profile, email, youtube.force-ssl, youtube.readonly)
   - access_type: 'offline' (obtém refresh_token na primeira autorização)
3. User autoriza → callback → Auth.js recebe access_token + refresh_token
4. Tokens salvos em Firestore: podcasts/{PODCAST_ID}/users/{userId}/tokens/oauth
   ⚠️ REGRA: refresh_token só é retornado na PRIMEIRA autorização.
   Salvar imediatamente e NUNCA sobrescrever em logins subsequentes.
   Callback jwt do Auth.js deve verificar se refresh_token já existe antes de persistir.
5. Session cookie (httpOnly) com JWT contendo userId
6. Middleware valida session cookie em cada request
7. Route Handlers buscam tokens no Firestore para YouTube API calls
8. Token refresh automático via Auth.js quando access_token expira

API & Communication Patterns

Decisão Escolha Rationale
SSE contract Hybrid (progress/field/complete/error) Alinhado ao UX progressive reveal + feedback de progresso
Error format Standard { error: { code, message, details? } } Simples, consistente, suficiente para o escopo
YouTube client Wrapper YouTubeClient com retry/quota Centraliza auth, retry, error handling
Gemini client Wrapper GeminiClient com streaming Centraliza prompt assembly, streaming, output parsing

SSE Event Contract:

// Event types enviados pelo server
type SSEEvent =
  | { event: 'progress', data: { percent: number, message: string } }
  | { event: 'field', data: { name: FieldName, value: unknown } }
  | { event: 'complete', data: { videoId: string } }
  | { event: 'error', data: { code: string, message: string } }

type FieldName = 'title' | 'description' | 'tags' | 'chapters' | 'compliance'

// Sequência típica:
// progress(10%, "Lendo transcrição...")
// progress(30%, "Gerando título...")
// field("title", "Como a IA mudou...")
// progress(50%, "Gerando descrição...")
// field("description", "Neste episódio...")
// progress(70%, "Gerando capítulos...")
// field("chapters", [...])
// progress(85%, "Gerando tags...")
// field("tags", [...])
// progress(95%, "Verificando compliance...")
// field("compliance", { status: "ok", items: [] })
// complete({ videoId: "abc123" })

Error Codes (enum):

type ErrorCode =
  | 'AUTH_EXPIRED'        // Token expirado, relogin necessário
  | 'YOUTUBE_QUOTA'       // Quota diária excedida
  | 'YOUTUBE_NOT_FOUND'   // Vídeo não encontrado
  | 'YOUTUBE_FORBIDDEN'   // Sem permissão no canal
  | 'GEMINI_TIMEOUT'      // LLM não respondeu a tempo
  | 'GEMINI_RATE_LIMIT'   // Rate limit do Gemini
  | 'GEMINI_INVALID'      // Output do LLM não passou Zod validation
  | 'FIRESTORE_ERROR'     // Erro de persistência
  | 'NETWORK_ERROR'       // Erro de rede genérico
  | 'VALIDATION_ERROR'    // Input inválido
  | 'BATCH_PARTIAL'       // Envio parcial (N de M falharam)

Frontend Architecture

Decisão Escolha Rationale
State management Zustand + URL state Zustand para runtime (videos, processing), URL para navegação (video selecionado)
Data fetching Plain fetch + Zustand Fetch manual em Route Handlers, store no Zustand. Sem magic revalidation.
Form handling Controlled + useAutoSave useState por campo, auto-save com debounce 1.5s. Alinhado ao UX spec.

Retry Pattern (SCOPE LIMITADO):

// ⚠️ withRetry é APENAS para:
// - Reads do Firestore (idempotentes)
// - YouTube API calls (GET, idempotentes)
// - Gemini API calls (idempotentes)
//
// ⚠️ NUNCA usar withRetry para:
// - Firestore writes (pode duplicar)
// - YouTube publish (POST/PUT)
//
// Para writes: "last write wins" via updatedAt timestamp
// Para operações atômicas: Firestore transactions

const MAX_RETRIES = 3
const BACKOFF_BASE = 1000

async function withRetry<T>(fn: () => Promise<T>, retries = MAX_RETRIES): Promise<T> {
  for (let i = 0; i < retries; i++) {
    try { return await fn() }
    catch (e) {
      if (i === retries - 1) throw e
      await sleep(BACKOFF_BASE * Math.pow(2, i))
    }
  }
  throw new Error('Unreachable')
}
