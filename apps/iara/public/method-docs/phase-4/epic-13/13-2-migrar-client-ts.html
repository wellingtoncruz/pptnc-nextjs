Story 13.2: Migrar client.ts — @google-cloud/vertexai → @google/genai

Status: done

Story

Como tech lead do IAra, Eu quero migrar o client.ts do SDK deprecated @google-cloud/vertexai para @google/genai, Para que o IAra use o SDK suportado antes do deadline de remoção (Jun 2026).

Contexto

Situação Atual

  • src/lib/llm/client.ts é o único ponto de chamada LLM para fases 1-7
  • Usa @google-cloud/vertexai (deprecated Jun 2025, remoção Jun 2026)
  • Singleton VertexAI + GenerativeModel com getModel()
  • Workaround undici para evitar UND_ERR_HEADERS_TIMEOUT em thinking longo
  • Workaround as Record<string, unknown> para thinkingConfig (sem tipo no SDK antigo)
  • Streaming via model.generateContentStream() com consumo de chunks + streamingResult.response
  • Response parsing: response.candidates?.[0]?.content?.parts?.[0]?.text

Mapeamento de API (confirmado pelo Spike 13.1)

Aspecto SDK Antigo SDK Novo
Import import { VertexAI, GenerativeModel } from '@google-cloud/vertexai' import { GoogleGenAI } from '@google/genai'
Init new VertexAI({ project, location }) → getGenerativeModel(...) new GoogleGenAI({ vertexai: true, project, location })
Model Singleton via getModel() Passado por chamada — sem singleton
Streaming model.generateContentStream({ contents, systemInstruction }) ai.models.generateContentStream({ model, contents, config })
System prompt { role: 'system', parts: [{ text }] } String direta em config.systemInstruction
Config generationConfig: { temperature, maxOutputTokens, ... } Campos diretos em config
thinkingConfig as Record<string, unknown> workaround Tipado nativamente
Response text response.candidates?.[0]?.content?.parts?.[0]?.text response.text (getter)
Usage response.usageMetadata?.promptTokenCount Idêntico
Timeout undici global dispatcher workaround Não necessário (stream mantém conexão)
Abort Não suportado config.abortSignal nativo

Arquivos Envolvidos

Arquivo Mudança

src/lib/llm/types.ts Minor — Remover VertexAIConfig, atualizar docs
src/lib/llm/index.ts Minor — Renomear export resetVertexAIClient → resetGenAIClient

NOTA: src/app/api/wizard/phase/5b/route.ts NÃO é modificado nesta story (será Story 13.3). NOTA: Testes NÃO são modificados nesta story (será Story 13.4).

Acceptance Criteria

AC1: Import e inicialização migrados

Given o arquivo client.ts When o dev revisa os imports Then não existe nenhum import de @google-cloud/vertexai And GoogleGenAI é importado de @google/genai And o client é inicializado com { vertexai: true, project, location }

AC2: Streaming funciona com novo SDK

Given uma chamada LLM via callLLM() When o modelo processa com streaming Then os chunks são iterados via for await (const chunk of stream) And a resposta final é extraída via response.text (getter do último chunk acumulado)

AC3: thinkingConfig sem workaround

Given a configuração do modelo When thinkingConfig é passado Then é tipado nativamente (sem as Record<string, unknown>)

AC4: undici workaround removido

Given o arquivo client.ts When o dev revisa o código Then não existe import de undici And não existe setGlobalDispatcher

AC5: Response parsing simplificado

Given uma resposta do modelo When o texto é extraído Then usa response.text (do último chunk da stream) ao invés de response.candidates[0].content.parts[0].text

AC6: systemInstruction simplificado

Given uma chamada LLM When o system prompt é passado Then usa config: { systemInstruction: text } (string direta) And não usa { role: 'system', parts: [{ text }] }

AC7: Singleton simplificado

Given o client When inicializado Then mantém apenas ai (GoogleGenAI) como singleton And remove vertexAI, generativeModel, currentModelName como state And remove getVertexAI(), getModel()

AC8: API pública preservada

Given a interface pública do módulo LLM When outros arquivos chamam callLLM, callLLMQueued, isLLMConfigured Then a assinatura e comportamento são idênticos And o arquivo index.ts continua exportando as mesmas funções

AC9: Build passa

Given a migração completa When pnpm build (ou tsc --noEmit no escopo de apps/iara) Then compila sem erros de tipo relacionados ao novo SDK

Dev Notes

Estrutura esperada após migração

import { GoogleGenAI } from '@google/genai'

// Singleton
let ai: GoogleGenAI | undefined
const DEFAULT_MODEL = 'gemini-2.5-flash'

function getAI(): GoogleGenAI {
  if (ai) return ai
  ai = new GoogleGenAI({
    vertexai: true,
    project: PROJECT_ID,
    location: GCP_REGION,
  })
  return ai
}

export function resetGenAIClient(): void {
  ai = undefined
}

// Core call
async function callGenAI<T>(
  systemPrompt: string,
  userPrompt: string,
  timeout: number,
  attachmentPath: string | undefined
): Promise<{ data: T; usage: ... }> {
  const client = getAI()
  const modelName = VERTEX_AI_MODEL || DEFAULT_MODEL

  // Build parts
  const parts = [{ text: userPrompt }]
  if (attachmentPath) {
    const base64 = await readFileAsBase64(attachmentPath)
    parts.push({ inlineData: { data: base64, mimeType: 'text/plain' } })
  }

  // Streaming call
  const stream = await client.models.generateContentStream({
    model: modelName,
    contents: parts,
    config: {
      systemInstruction: systemPrompt,
      responseMimeType: 'application/json',
      temperature: 0.7,
      maxOutputTokens: 65536,
      thinkingConfig: { thinkingBudget: 24576 },
    },
  })

  // Consume stream
  let lastResponse
  for await (const chunk of stream) {
    lastResponse = chunk
  }

  const text = lastResponse?.text
  // ... parse, retry, etc.
}

readFileAsBase64 mantido

O inlineData.data no novo SDK continua sendo string base64 — a função readFileAsBase64 é necessária.

Stream response pattern

No SDK antigo: streamingResult.stream (chunks) + streamingResult.response (aggregated). No SDK novo: stream retorna AsyncGenerator<GenerateContentResponse> — cada chunk é um response parcial. O último chunk contém os dados finais. Usar response.text e response.usageMetadata do último chunk.

Timeout handling

O undici workaround (headersTimeout: 0) resolvia o problema de timeout HTTP durante thinking. No novo SDK, o streaming mantém a conexão ativa (cada chunk é um keep-alive). Se mesmo assim ocorrer timeout, PHASE_TIMEOUTS com valor 0 (fases 1-4) significa "sem timeout". Para fases 5-7 (timeout 120s), o timeout do fetch nativo deve ser suficiente.
