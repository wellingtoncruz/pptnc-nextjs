Story 14.6: Schema socialPosts, API Endpoints e Subcollection

Status: done

Story

As a sistema, I want persistir e recuperar posts sociais gerados pela IA no Firestore, so that os posts sejam armazenados por vídeo e por rede social com validação e endpoints dedicados.

Prerequisites

BLOQUEANTES — Devem estar implementadas ANTES de iniciar esta story:

  • Story 14.2 — SocialNetworkSchema + getSocialNetworks() + collection global socialNetworks
  • Story 14.4 — enabledSocialNetworks[] no PodcastSchema
  • Story 14.5 — prompts[videoType].social[networkId] nos schemas de prompts

Acceptance Criteria

  1. Schema SocialPostSchema — Em src/lib/schemas/social.ts, valida:

    {
  networkId: z.string().min(1),
  cta: z.string(),
  body: z.string(),
  hashtags: z.array(z.string()),
  additionalContext: z.string().optional(),
  generatedAt: TimestampSchema,
  updatedAt: TimestampSchema,
  processedBy: z.enum(['llm', 'manual'])
}

  2. Schema SocialPostUpdateSchema — Para validação do body do PUT: { cta, body, hashtags } (sem timestamps nem processedBy — gerenciados pelo servidor).

  3. Admin getSocialPosts(videoId) — Em social-admin.ts, retorna SocialPost[] da subcollection podcasts/{podcastId}/videos/{videoId}/socialPosts. Documentos inválidos são logados como warning e ignorados (padrão safeParse de getSocialNetworks).

  4. Admin upsertSocialPost(videoId, networkId, data) — Em social-admin.ts, faz upsert no documento socialPosts/{networkId} com field-level merge. Seta updatedAt via FieldValue.serverTimestamp() e processedBy: 'manual'.

  5. GET /api/videos/[videoId]/social-posts — Retorna { data: SocialPost[] } (pode ser vazio). Auth obrigatória (401 se sem sessão). Response validada com Zod antes de retornar.

  6. PUT /api/videos/[videoId]/social-posts/[networkId] — Aceita { cta, body, hashtags } no body. Valida com Zod ANTES de persistir. Seta processedBy: 'manual' e updatedAt: serverTimestamp(). Retorna { data: { networkId } }. Auth obrigatória (401).

  7. Testes — Testes para schema (social.test.ts), admin operations (social-admin.test.ts), e API routes (route.test.ts para cada endpoint). Todos os testes existentes continuam passando.

Padrões Existentes a Seguir

Route Handler pattern (tags/route.ts:38-91):

export const runtime = 'nodejs'

interface RouteContext {
  params: Promise<{ videoId: string }>
}

export async function PUT(request: NextRequest, context: RouteContext): Promise<NextResponse> {
  const session = await auth()
  if (!session) return authExpiredResponse()

  const { videoId } = await context.params

  try {
    const body = await request.json()
    const validated = Schema.parse(body)
    // ... persist
    log('INFO', 'Resource updated', { videoId })
    return NextResponse.json({ data: { ... } })
  } catch (error) {
    return handleVideoFieldError(error, 'fieldName', videoId)
  }
}

IMPORTANTE — context.params é Promise: No Next.js 15, context.params retorna Promise. Sempre await context.params antes de desestruturar.

PUT com nested route ([videoId]/social-posts/[networkId]/route.ts):

interface RouteContext {
  params: Promise<{ videoId: string; networkId: string }>
}

Admin safeParse pattern (social-admin.ts:33-43):

for (const doc of snapshot.docs) {
  const parsed = Schema.safeParse({ ...doc.data(), id: doc.id })
  if (parsed.success) {
    items.push(parsed.data)
  } else {
    log('WARN', 'Invalid document skipped', { id: doc.id, issues: parsed.error.issues })
  }
}

Subcollection path (enforcement rule #8):

const postsRef = db
  .collection('podcasts').doc(PODCAST_ID)
  .collection('videos').doc(videoId)
  .collection('socialPosts')

Upsert com merge (para upsertSocialPost):

// Usar set com merge para criar OU atualizar
await docRef.set({
  ...validated,
  processedBy: 'manual',
  updatedAt: FieldValue.serverTimestamp(),
}, { merge: true })

Nota: Aqui set({ merge: true }) é preferível a update() porque o documento pode não existir ainda (primeiro save manual ou LLM cria o doc). update() falha se doc não existe. set({ merge: true }) cria ou atualiza.

Error handler reutilizável (video-field-handler.ts):

  • authExpiredResponse() → 401 AUTH_EXPIRED
  • notFoundResponse(resource) → 404 NOT_FOUND
  • handleVideoFieldError(error, fieldName, videoId) → 400/500
  • createErrorResponse(code, message, status) → custom

Imports:

import { auth } from '@/lib/auth'
import { PODCAST_ID } from '@/lib/firebase/config'
import { log } from '@/lib/logger'
import { authExpiredResponse, handleVideoFieldError } from '@/lib/api/video-field-handler'

Timestamp no Schema

O SocialPostSchema é usado para leitura do Firestore — portanto usa TimestampSchema (custom Timestamp validator, já exportado de podcast.ts). O SocialPostUpdateSchema para escrita NÃO inclui timestamps (o servidor seta via FieldValue.serverTimestamp()).

PODCAST_ID

Importar de @/lib/firebase/config:

import { PODCAST_ID } from '@/lib/firebase/config'

O PODCAST_ID vem de process.env.PODCAST_ID (enforcement rule #8).

Schema de Testes — Mock de Firestore

Os testes de social-admin.test.ts devem seguir o padrão existente. Verificar src/lib/firebase/social-admin.test.ts (já existe com 6 testes para getSocialNetworks). Estender esse arquivo com testes para as novas funções.
