Story 14.7: Processamento LLM Sequencial para Posts Sociais

Status: done

Story

As a sistema, I want processar posts sociais via LLM usando a persona socialmedia, so that cada rede social receba um post otimizado para sua plataforma.

Prerequisites

BLOQUEANTES — Devem estar implementadas ANTES de iniciar esta story:

  • Story 14.1 — Persona socialmedia (Gerente de Mídia) no PersonasSchema
  • Story 14.5 — prompts[videoType].social[networkId] nos schemas de prompts
  • Story 14.6 — SocialPostSchema, SocialPostUpdateSchema, getSocialPosts(), upsertSocialPost(), API endpoints GET/PUT

Acceptance Criteria

  1. Endpoint POST /api/videos/[videoId]/social-posts/[networkId]/generate — Recebe { additionalContext?: string } no body (max 500 chars). Auth obrigatória (401 se sem sessão). Retorna { data: { networkId, cta, body, hashtags, processedBy: 'llm' } } após geração e persistência.

  2. Prompt building — Constrói system prompt seguindo template:

    Seu papel: {persona.socialmedia.role}
Seu objetivo: {persona.socialmedia.objective}
Seu contexto: {persona.socialmedia.resume}

## TAREFA
{prompts[videoType].social[networkId].description}

## Formato
{prompts[videoType].social[networkId].expectedOutput}

[JSON schema fixo: { cta, body, hashtags }]

    Usa callGenAI diretamente (NÃO callLLM/callLLMQueued que são específicos de WizardPhase).

  3. Contexto do vídeo no user prompt — Inclui título, duração formatada, descrição, tipo e tema. Para cut/reel, busca vídeo pai via getVideoAdmin(PODCAST_ID, parentEpisodeId) e inclui bloco extra com dados do pai. Transcrição condicional por tipo de vídeo: para cut e reel, a transcrição (transcriptionTXT) é anexada como arquivo via createTranscriptionFile() (vídeos curtos — custo-benefício positivo). Para episodes, NÃO anexar transcrição (custo de tokens não justifica o benefício para geração de post social).

  4. additionalContext — Se fornecido no body do POST, adiciona ao final do system prompt: "Dê uma atenção especial a essa instrução: {additionalContext}". O valor é persistido no documento para referência.

  5. Processamento sequencial — Usa llmQueue.enqueue() para garantir processamento sequencial. Compartilha fila com o Wizard (singleton).

  6. Parse do retorno LLM — Resposta parseada como JSON: { cta: string, body: string, hashtags: string[] }. Validada com SocialPostUpdateSchema.parse() (reusa schema da Story 14.6). Se parse falhar, callGenAI faz retry automático (até 3x).

  7. Persistência com processedBy: 'llm' — Nova função saveSocialPostFromLLM() em social-admin.ts persiste o post com processedBy: 'llm', generatedAt: serverTimestamp(), updatedAt: serverTimestamp(), e additionalContext opcional.

  8. Graceful degradation para persona ausente — Se podcast.personas.socialmedia é undefined, usa strings vazias para role/objective/resume. Log WARN indicando fallback.

  9. Erro: prompt não configurado — Se prompts[videoType].social[networkId] não existe ou description está vazio, retorna 400 { error: { code: 'MISSING_PROMPT', message: 'Prompt não configurado para {networkId}' } }. NÃO faz chamada ao LLM.

  10. Erro: pré-requisitos do vídeo — Se o vídeo não possui title, theme ou description (otimizados), retorna 400 { error: { code: 'MISSING_PREREQUISITES', message: '...' } }. NÃO faz chamada ao LLM.

  11. Erro LLM — Erros do callGenAI (rate limit, timeout, parse error) são capturados e retornados como { error: { code, message } }. Rate limit → 429. Parse/timeout → 500. Post incompleto NÃO é persistido.

  12. Testes — Testes para social-prompts.ts (prompt building), saveSocialPostFromLLM em social-admin.test.ts, e testes da route generate/route.test.ts.

Dev Notes

Arquitetura e Padrões

  • callGenAI direto, NÃO callLLM/callLLMQueued: As funções callLLM e callLLMQueued são tipadas com WizardPhase (1-7) e usam PHASE_CONFIG, buildPhasePrompt, validateVideoForPhase, e transcription handling. Para social posts, nenhuma dessas é aplicável. Usar callGenAI<T>() diretamente com llmQueue.enqueue() para processamento sequencial.

  • Transcrição condicional por tipo de vídeo: Para cut e reel (vídeos curtos, transcrições pequenas), a transcrição transcriptionTXT é anexada como arquivo via createTranscriptionFile(content, 0) / cleanupTranscriptionFile(path) — phase=0 é a convenção para processamento social (o parâmetro é number, usado no filename do temp). O custo de tokens é baixo e o contexto enriquece o post. Para episodes (transcrições longas de 30-60 min), NÃO anexar transcrição — o custo de tokens não justifica o benefício para geração de post social; os metadados (título, descrição, tema) são suficientes. Usar helper shouldAttachTranscription(video): boolean em social-prompts.ts para encapsular a decisão: return video.videoType !== 'episode' && !!video.transcriptionTXT.

  • llmQueue é singleton compartilhado: A fila llmQueue exportada de @/lib/llm/queue é a mesma usada pelo Wizard. Isso garante que processamento social e processamento de fases do Wizard nunca executam em paralelo (evita rate limit do Gemini).

  • callGenAI já faz retry de PARSE_ERROR: O callGenAI internamente faz até 3 retries em caso de PARSE_ERROR (com 1s de delay). Não é necessário adicionar retry no route handler — se o LLM não retornar JSON válido após 3 tentativas, callGenAI lança LLMError com code PARSE_ERROR.

  • responseMimeType: 'application/json': O callGenAI já configura Gemini com responseMimeType: 'application/json', o que melhora significativamente a taxa de parse. O SOCIAL_POST_JSON_SCHEMA reforça o formato no prompt.

  • SocialPostUpdateSchema reutilizado para validação de LLM: O schema { cta, body, hashtags } do 14.6 é idêntico ao formato de retorno do LLM. Usar .parse() para validar antes de persistir.

  • saveSocialPostFromLLM separada de upsertSocialPost: A função upsertSocialPost (14.6) hardcoda processedBy: 'manual'. Para LLM, criamos função separada que seta processedBy: 'llm' e generatedAt. Manter separado evita alterar código já testado da 14.6.

  • Helper getSocialPostsCollection(videoId) compartilhado: Extrair helper privado que constrói o path podcasts/${PODCAST_ID}/videos/${videoId}/socialPosts e refatorar getSocialPosts, upsertSocialPost e saveSocialPostFromLLM para usá-lo. Evita duplicação de path (seguindo padrão de getGuestsCollection existente).

  • Timeout de 60s (não 120s): Prompts sociais recebem ~500-2000 tokens de contexto (vs transcrições de 50K+ do Wizard). Timeout de 60000ms é suficiente e protege melhor contra bloquear a fila por tempo excessivo.

  • Body do request totalmente opcional: O POST aceita body { additionalContext?: string } mas também aceita body vazio ou ausente. O pattern request.json().catch(() => ({})) é usado intencionalmente — diferente de endpoints que exigem body (ex: PUT que valida campos obrigatórios). O additionalContext é para reprocessamento (Story 14.10) e na primeira geração normalmente não é enviado.

  • getPodcastAdmin retorna Podcast | null: Se o podcast não existir, retorna null. O route handler deve tratar: if (!podcast) return notFoundResponse('Podcast'). Para uso no prompt building, passar podcast.personas?.socialmedia (optional chaining) já que socialmedia é .optional() no schema (Story 14.1).

  • Prompt building puro (sem I/O): buildSocialSystemPrompt e buildSocialUserPrompt são funções puras (sem fetch/Firestore). O route handler é responsável por buscar dados e passar como parâmetros. Isso facilita testes unitários.

  • Parent video para cut/reel: O route handler verifica video.parentEpisodeId para cut/reel e busca o vídeo pai. O pai é passado como parâmetro opcional para buildSocialUserPrompt. Se o pai não for encontrado (edge case: vídeo deletado), o user prompt inclui apenas dados do vídeo atual (graceful degradation).

  • Error codes novos: MISSING_PROMPT e MISSING_PREREQUISITES são codes de API (não de LLM). Retornados como 400 pelo route handler via createErrorResponse().
