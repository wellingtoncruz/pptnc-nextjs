Story 14.3: Feature Toggle socialMedia em Configurações → Recursos

Status: done

Story

As a administrador do podcast, I want habilitar/desabilitar a funcionalidade de Redes Sociais, so that eu controle a visibilidade da seção no menu lateral e nas configurações.

Acceptance Criteria

  1. Schema estendido — O features object em src/lib/schemas/podcast.ts inclui socialMedia: z.boolean().default(false). Default false para backward-compatibility (podcasts existentes não veem a seção até habilitarem).

  2. Toggle na UI — Na tela Configurações → Recursos, há quatro toggles: Editorial, Notícias, Incluir Livestreams, Redes Sociais. O toggle "Redes Sociais" segue o mesmo padrão visual (Switch do shadcn/ui).

  3. Save funciona — Ao ativar/desativar o toggle "Redes Sociais", o features.socialMedia é salvo via PATCH /api/podcast com { features: { editorial, news, includeLivestreams, socialMedia } }. Update optimistic com rollback on error.

  4. Backward-compatible — Podcasts existentes sem features.socialMedia no Firestore continuam funcionando. O schema default garante false, e a UI renderiza o toggle como desabilitado.

  5. Testes atualizados — Testes do features-settings-form.test.tsx verificam renderização e toggle da quarta feature.

Tasks / Subtasks

  • Task 1: Estender FeaturesSchema (AC: #1, #4)

    • 1.1 Adicionado socialMedia: z.boolean().default(false) ao features object em podcast.ts

  • Task 2: Atualizar FeaturesSettingsForm (AC: #2, #3)

    • 2.1 Interface PodcastFeatures, useState, setters, handleToggle union type, e toggle UI atualizados

  • Task 3: Atualizar Settings Page Client (AC: #3, #4)

  • Task 4: Atualizar testes (AC: #5)

    • 4.2 settings-page-client.test.tsx: mockPodcast sem features testa fallback ?? false — renderiza sem erro (verificado).

  • Task 5: Validar integração

    • 5.1 npx vitest run — 1770 testes passando (93 test files)
    • 5.2 PodcastUpdateSchema herda socialMedia automaticamente via Zod inference — PATCH aceita o campo

Dev Notes

Arquitetura e Padrões

  • Optimistic update com rollback: O FeaturesSettingsForm atualiza o estado local imediatamente no toggle, faz PATCH ao API, e reverte se o API retornar erro. Esse padrão já existe para editorial, news, includeLivestreams — basta replicar para socialMedia.
  • Objeto setters: O componente usa um lookup object setters que mapeia feature key → setter function. Adicionar socialMedia: setSocialMedia.
  • handleToggle envia objeto completo: Cada toggle envia TODAS as features no PATCH (não apenas a alterada). Isso porque o features é um campo nested que é substituído inteiro no Firestore. Ao adicionar socialMedia, garantir que é incluído no spread.
  • Default false: Diferente de editorial (default true) e news (default true), o socialMedia usa default false. Isso garante que podcasts existentes NÃO veem a seção até habilitarem explicitamente.
  • Escopo desta story: Esta story adiciona APENAS o toggle. A visibilidade condicional do accordion "Redes Sociais" nas Configurações é Story 14.4. A visibilidade no sidebar é Story 14.8.

handleToggle (features-settings-form.tsx):

async function handleToggle(key: 'editorial' | 'news' | 'includeLivestreams', value: boolean) {
  const updated = { editorial, news, includeLivestreams, [key]: value }
  setters[key]?.(value)
  setSaving(true)
  setError(null)

  try {
    await updateFeaturesViaApi(updated)
  } catch {
    setters[key](!value)  // rollback: simplesmente nega o valor
    setError('Erro ao salvar. Tente novamente.')
  } finally {
    setSaving(false)
  }
}

Nota: O key é union type (não string). Adicionar | 'socialMedia' ao union. O rollback usa !value (não previous lookup). Incluir socialMedia no objeto updated.

Props no settings-page-client (settings-page-client.tsx:175-187):

<FeaturesSettingsForm features={{
  editorial: podcast.features?.editorial ?? true,
  news: podcast.features?.news ?? true,
  includeLivestreams: podcast.features?.includeLivestreams ?? false,
}} />

Backward Compatibility

O campo socialMedia usa .default(false) no Zod schema. Podcasts existentes no Firestore sem este campo terão false como default ao fazer parse. A UI renderiza o toggle como desabilitado. O campo features em si é .optional() no PodcastSchema — o fallback ?? false no settings-page-client.tsx garante que a UI funciona mesmo sem o campo.

Learnings das Stories Anteriores

  • Story 14.1: union types devem ser atualizados em todas as interfaces/type annotations
  • Story 14.1: labels PT-BR devem ser verificados contra o código existente
  • Story 14.2: id não deve ser duplicado como campo e como doc ID
  • Testes de features devem incluir TODOS os campos no body esperado do PATCH (não omitir nenhum toggle)
