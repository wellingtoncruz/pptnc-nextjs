Epic 14: Redes Sociais — Posts Otimizados para Divulgação

Status: backlog

Objetivo

Ampliar as capacidades do IAra para preparar posts otimizados de divulgação dos artefatos produzidos no podcast através das redes sociais. O produtor terá acesso a textos escritos por uma persona especialista em redação publicitária (Gerente de Mídia), com posts específicos para cada rede social habilitada.

Contexto

O IAra já gera metadados otimizados para YouTube (título, descrição, tags, capítulos). O próximo passo natural é estender essa inteligência para as redes sociais, onde o produtor precisa divulgar cada episódio/corte/reel. Hoje, o produtor escreve manualmente os posts para Instagram, LinkedIn etc. — um trabalho repetitivo que a IA pode automatizar com qualidade.

A arquitetura segue o padrão já consolidado no IAra: persona LLM configurável, prompts por tipo de vídeo, processamento sequencial via fila, edição inline com auto-save, e feature toggle para controle de visibilidade.

Escopo

Incluído nesta Epic

  • Nova persona LLM: socialmedia (Gerente de Mídia) nas configurações do podcast
  • Collection global socialNetworks com catálogo de redes disponíveis
  • Seeding inicial: Instagram e LinkedIn
  • Seção "Redes Sociais" nas Configurações para habilitação/desabilitação por podcast
  • Prompts por rede social por tipo de vídeo (prompts[videoType].social[networkId])
  • Feature toggle "Redes Sociais" em Configurações → Recursos
  • Subcollection socialPosts/{networkId} por vídeo para persistência
  • Processamento LLM sequencial (reutiliza queue.ts) com persona socialmedia
  • Nova seção "Redes Sociais" no menu lateral com sidebar de vídeos
  • Layout de colunas fixas (640px) com scroll horizontal por rede habilitada
  • Edição inline (CTA, body, hashtags) com auto-save debounce 1.5s
  • Reprocessamento com additionalContext (como fases Tipo 1 do Wizard)
  • Copy to clipboard por campo (CTA, body, hashtags)
  • Atualização do seed script e guia de onboarding

Fora de Escopo (Futuras Epics)

  • Integração direta com APIs das redes sociais (publicação automática)
  • Configuração de OAuth tokens para redes sociais (preparado no schema, não implementado)
  • Agendamento de posts
  • Preview visual do post (mockup de como ficará na rede)
  • Analytics de engajamento dos posts

Decisões Técnicas

Decisão Escolha Justificativa
Persona LLM socialmedia (Gerente de Mídia) Persona específica para redação publicitária, separada de writer e critic
Catálogo de redes Collection global socialNetworks/{networkId} Redes adicionadas via banco de dados, habilitadas por podcast
Habilitação por podcast Campo enabledSocialNetworks: string[] em podcasts/{podcastId} Cada tenant escolhe suas redes independentemente
Persistência de posts Subcollection podcasts/{podcastId}/videos/{videoId}/socialPosts/{networkId} Flexível para N redes, não sobrecarrega documento do vídeo
Prompts por rede prompts[videoType].social[networkId].{description,expectedOutput} Extensão natural da estrutura existente de prompts
Processamento Sequencial via queue.ts existente Evita rate-limit, reutiliza infraestrutura consolidada
Pré-condição de vídeo Título + tema + descrição já otimizados Não exige todas as fases do Wizard, apenas dados mínimos
Edição Auto-save com debounce 1.5s Consistente com padrão do Wizard
Feature toggle Estende features existente do Epic 13 features.socialMedia: boolean no documento do podcast
Visibilidade da seção Feature toggle habilitado E pelo menos uma rede habilitada Dupla condição evita seção vazia
Colunas de layout 640px fixo por coluna, scroll horizontal Layout claro para comparação side-by-side
Hashtags Texto livre (não badge/chips) Simplifica edição — produtor copia texto direto

}

Schema: socialPosts/{networkId} (Subcollection por Vídeo)

{
  networkId: string              // 'instagram' | 'linkedin' | ...
  cta: string                    // Call to Action
  body: string                   // Corpo do post
  hashtags: string[]             // Array de hashtags
  additionalContext?: string     // Contexto usado no último reprocessamento
  generatedAt: Timestamp         // Quando foi gerado pelo LLM
  updatedAt: Timestamp           // Última edição (manual ou reprocessamento)
  processedBy: 'llm' | 'manual' // Origem da última versão
}

Schema: Habilitação no Podcast

// Em podcasts/{podcastId}
{
  enabledSocialNetworks: string[]  // ['instagram', 'linkedin']
  features: {
    editorial: boolean,

    socialMedia: boolean  // NOVO — toggle de visibilidade da seção
  }
}

Detalhamento por Story

Story 14.1: Schema e Persona socialmedia (Gerente de Mídia)

Como um administrador do podcast, Eu quero configurar uma persona especialista em redes sociais (Gerente de Mídia), Para que a IA gere posts com tom e estilo de redação publicitária profissional.

Acceptance Criteria:

Given o schema PersonasSchema em src/lib/schemas/podcast.ts When eu adiciono a persona socialmedia Then o schema inclui uma terceira persona com os mesmos campos das existentes:

  • socialmedia: { role: z.string().max(1000), objective: z.string().max(2000), resume: z.string().max(5000) } And as constraints de max-length seguem as constantes existentes: MAX_ROLE_LENGTH, MAX_OBJECTIVE_LENGTH, MAX_RESUME_LENGTH And todos os campos são opcionais (.optional()) para backward-compatibility com podcasts existentes

Given a tela de Configurações → Personas do LLM When o administrador expande a seção de Personas Then vê três personas configuráveis: Crítico, Redator, Gerente de Mídia And a nova persona segue o mesmo layout das existentes (role, objective, resume como textareas) And o auto-save funciona via PATCH /api/podcast com { personas: { socialmedia: {...} } }

Given um podcast existente sem a persona socialmedia When o schema faz parse do documento Then a persona socialmedia é undefined (sem breaking change) And o processamento LLM usa fallback para campos vazios (comportamento a definir na Story 14.7)

Arquivos:

  • src/lib/schemas/podcast.ts — estender PersonasSchema com socialmedia
  • src/components/settings/personas-settings-form.tsx — adicionar seção para Gerente de Mídia

Technical Notes:

  • Seguir exatamente o padrão de critic e writer no schema
  • O label na UI deve ser "Gerente de Mídia" (não "Social Media")
  • A chave no Firestore é personas.socialmedia

Story 14.2: Collection Global socialNetworks + Seed

Como um sistema, Eu quero uma collection global de redes sociais disponíveis no Firestore, Para que novos tenants possam ver e habilitar redes sociais sem alteração de código.

Acceptance Criteria:

Given a necessidade de um catálogo de redes sociais When eu crio a collection socialNetworks Then existe um schema Zod SocialNetworkSchema em src/lib/schemas/social.ts:

{
  id: string        // 'instagram', 'linkedin'
  name: string      // 'Instagram', 'LinkedIn'
  icon: string      // Emoji: '📸', '💼' (ou similar)
  createdAt: Timestamp
}

Given o seed script scripts/seed-podcast.ts When executado para um novo podcast Then cria dois documentos na collection global socialNetworks (se não existirem):

  • socialNetworks/instagram: { id: 'instagram', name: 'Instagram', icon: '📸' }
  • socialNetworks/linkedin: { id: 'linkedin', name: 'LinkedIn', icon: '💼' } And a criação é idempotente (não sobrescreve se já existir)

Given a collection socialNetworks When um admin adiciona uma nova rede diretamente no Firestore Then a nova rede aparece automaticamente na seção de Configurações → Redes Sociais (Story 14.4) And nenhuma alteração de código é necessária

Given operações de leitura da collection When eu uso getSocialNetworks() Then retorna array de SocialNetwork[] validado com Zod And ordenado por name ascendente

Arquivos:

  • src/lib/schemas/social.ts — novo arquivo com SocialNetworkSchema, SocialPostSchema
  • src/lib/firebase/social-admin.ts — novo arquivo com getSocialNetworks()
  • scripts/seed-podcast.ts — adicionar seed de socialNetworks

Technical Notes:

  • Collection global (não por podcast): socialNetworks/{networkId}
  • Usar Firebase Admin SDK para leitura (server-side only)
  • O seed é idempotente: verifica existência antes de criar
  • Novos networks podem ser criados manualmente via Firestore Console

Story 14.5: Prompts por Rede Social por Tipo de Vídeo

Como um administrador do podcast, Eu quero configurar prompts específicos para cada rede social e tipo de vídeo, Para que a IA gere posts otimizados para cada plataforma.

Acceptance Criteria:

Given o schema PromptsSchema em src/lib/schemas/podcast.ts When eu estendo para incluir prompts sociais Then cada tipo de vídeo (episode, cut, reel) ganha um campo social:

social: z.record(z.string(), PromptFieldSchema).optional()
// Onde a chave é o networkId e PromptFieldSchema = { description, expectedOutput }

And z.record() permite N redes sem alterar o schema ao adicionar novas redes

Given a tela de Configurações → Prompts por Tipo de Vídeo When o administrador expande um tipo de vídeo (ex: Episode) Then além dos prompts existentes (Critique, Titles, etc.), vê uma subseção "Redes Sociais" And para cada rede habilitada em enabledSocialNetworks, exibe dois campos:

  • "Descrição do Prompt" (textarea) — mapeia para prompts[videoType].social[networkId].description
  • "Saída Esperada" (textarea) — mapeia para prompts[videoType].social[networkId].expectedOutput And cada par de campos é identificado com label {icon} {networkName}

Given o administrador edita um prompt social When ele modifica o texto Then o auto-save é acionado após 1.5s via PATCH /api/podcast And salva em prompts.{videoType}.social.{networkId}.{description|expectedOutput}

Given uma rede social é desabilitada após ter prompts configurados When o administrador visualiza Prompts Then os prompts da rede desabilitada NÃO aparecem na UI And os dados permanecem no Firestore (não são deletados)

Given nenhuma rede social habilitada When o administrador visualiza Prompts Then a subseção "Redes Sociais" NÃO aparece dentro dos tipos de vídeo

Arquivos:

  • src/lib/schemas/podcast.ts — estender cada tipo de prompt com campo social: z.record(...).optional()
  • src/components/settings/prompts-settings-form.tsx — adicionar subseção "Redes Sociais" por videoType

Technical Notes:

  • Usar z.record(z.string(), PromptFieldSchema) em vez de campos fixos por rede — isso permite adicionar redes sem mudar o schema
  • O PromptFieldSchema existente ({ description: z.string().max(MAX_PROMPT_LENGTH), expectedOutput: z.string().max(MAX_PROMPT_LENGTH) }) é reutilizado
  • A subseção de redes só aparece se enabledSocialNetworks.length > 0
  • Os prompts sociais são renderizados dinamicamente baseado nas redes habilitadas

Story 14.6: Schema socialPosts, API Endpoints e Subcollection

Como um sistema, Eu quero persistir e recuperar posts sociais gerados pela IA no Firestore, Para que os posts sejam armazenados por vídeo e por rede social.

Acceptance Criteria:

Given a necessidade de persistir posts sociais When eu crio o schema SocialPostSchema em src/lib/schemas/social.ts Then o schema valida:

{
  networkId: z.string(),
  cta: z.string(),
  body: z.string(),
  hashtags: z.array(z.string()),
  additionalContext: z.string().optional(),
  generatedAt: TimestampSchema,
  updatedAt: TimestampSchema,
  processedBy: z.enum(['llm', 'manual'])
}

Given o endpoint GET /api/videos/[videoId]/social-posts When chamado com vídeo válido Then retorna todos os social posts da subcollection podcasts/{podcastId}/videos/{videoId}/socialPosts And cada documento tem o networkId como document ID And response validada com Zod antes de retornar And retorna { data: SocialPost[] } (array, pode ser vazia)

Given o endpoint PUT /api/videos/[videoId]/social-posts/[networkId] When chamado com body válido { cta, body, hashtags } Then atualiza o documento socialPosts/{networkId} com field-level merge And updatedAt é atualizado com serverTimestamp() And processedBy é definido como 'manual' And retorna { data: { networkId, updatedAt } }

Given o endpoint PUT /api/videos/[videoId]/social-posts/[networkId] When chamado sem autenticação Then retorna 401 { error: { code: 'AUTH_EXPIRED' } }

Given a subcollection path When eu acesso via Admin SDK Then o path é podcasts/{podcastId}/videos/{videoId}/socialPosts/{networkId} And usa podcastId do env var PODCAST_ID (enforcement rule #8)

Arquivos:

  • src/lib/schemas/social.ts — SocialPostSchema, SocialPostCreateSchema
  • src/lib/firebase/social-admin.ts — getSocialPosts(videoId), upsertSocialPost(videoId, networkId, data)
  • src/app/api/videos/[videoId]/social-posts/route.ts — novo GET endpoint
  • src/app/api/videos/[videoId]/social-posts/[networkId]/route.ts — novo PUT endpoint

Technical Notes:

  • Seguir padrão de Route Handlers existentes: export const runtime = 'nodejs'
  • Validar input com Zod ANTES de persistir (enforcement rule #2)
