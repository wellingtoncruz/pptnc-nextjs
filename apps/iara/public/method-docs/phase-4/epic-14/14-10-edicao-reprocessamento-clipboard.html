Story 14.10: Edição Inline, Reprocessamento e Copy to Clipboard

Status: done

Story

As a produtor, I want editar os posts gerados, reprocessar com instruções adicionais, e copiar para a área de transferência, so that eu possa ajustar os textos e usá-los nas redes sociais.

Prerequisites

BLOQUEANTES — Devem estar implementadas ANTES de iniciar esta story:

  • Story 14.6 — API endpoints PUT social-posts (backend ready)
  • Story 14.7 — POST endpoint de geração LLM com additionalContext (backend ready)
  • Story 14.9 — SocialPostColumn com exibição de posts (componente base a estender)

Acceptance Criteria

  1. Edição do CTA — Ao clicar no CTA de um post exibido, o campo se torna editável (input text). Auto-save com debounce 1.5s via PUT /api/videos/{videoId}/social-posts/{networkId}. processedBy muda para 'manual'. Indicador "Salvo" aparece após save bem-sucedido.

  2. Edição do Body — Ao clicar no body, o campo se torna editável (textarea com auto-resize). Auto-save com debounce 1.5s. processedBy muda para 'manual'.

  3. Edição de Hashtags — Campo é textarea de texto livre (NÃO badges/chips). Auto-save com debounce 1.5s. Hashtags são parseadas como array antes de salvar: split por espaço ou vírgula, remover duplicatas, adicionar # se ausente.

  4. Reprocessamento com additionalContext — Botão "Reprocessar" exibe textarea de additionalContext (max 500 chars). Botão "Gerar novamente" confirma e chama POST /api/videos/{videoId}/social-posts/{networkId}/generate com { additionalContext }. Spinner substitui conteúdo durante processamento. Ao completar: exibe novo post, dados anteriores sobrescritos.

  5. Copiar CTA — Botão "Copiar" ao lado do CTA usa navigator.clipboard.writeText(). Feedback visual: ícone muda de Copy para Check por 2 segundos.

  6. Copiar Body — Botão "Copiar" ao lado do body copia texto para clipboard com mesmo feedback visual.

  7. Copiar Hashtags — Botão "Copiar" nas hashtags copia como texto separado por espaço com #. Mesmo feedback visual.

  8. Testes — Testes para SocialPostEditor (edição inline, auto-save com debounce, hashtags parsing), CopyButton (clipboard, feedback visual), reprocessamento (modal, POST call, spinner, resultado).

Dev Notes

Arquitetura e Padrões

  • useAutoSave hook existente: O hook src/hooks/use-auto-save.ts já implementa exatamente o padrão necessário: debounce 1.5s, deep comparison via JSON.stringify, status cycle idle → pending → saving → saved → idle, error handling. NÃO reimplementar — usar diretamente.

  • SaveStatusIndicator existente: O componente src/components/settings/save-status-indicator.tsx já renderiza indicadores "Alterações pendentes...", "Salvando...", "Salvo" baseado no saveStatus. Reutilizar diretamente.

  • Composição de combinedValue: O useAutoSave recebe um valor genérico T e compara via JSON.stringify. Para os 3 campos (CTA, body, hashtags), compor um objeto { cta, body, hashtags } como valor único. Assim, qualquer mudança em qualquer campo dispara o debounce e salva todos os 3 campos de uma vez via PUT.

  • ParseHashtags como pura function: Extrair parseHashtags(text: string): string[] como função pura (não hook). Facilita testes isolados via test.each. Regras: split /[\s,]+/, filter vazias, map s => s.startsWith('#') ? s : '#' + s, dedup case-insensitive.

  • CopyButton standalone: Componente simples e reutilizável. Sem dependência de contexto externo. Recebe text, copia, gerencia state local de copied. Pode ser reutilizado em qualquer lugar do app futuramente.

  • Reprocessamento como prop callback: O SocialPostColumn não faz o POST diretamente. Recebe onReprocess como callback do parent (SocialColumnsLayout), que delega para useSocialPosts.reprocessNetwork(). Isso mantém a separação de responsabilidades: coluna = UI, hook = lógica.

  • Auto-save vs reprocessamento: Se o produtor edita um campo e depois clica "Reprocessar" antes do debounce completar, o auto-save pendente deve ser cancelado. O reprocessamento sobrescreve tudo com novo conteúdo LLM. Implementar: ao iniciar reprocessamento, reinicializar os estados de edição com o novo post quando ele retornar.

  • EditableText NÃO usado aqui: O componente EditableText existente é click-to-edit com Input (single line, Enter saves, Escape cancels). Para social posts, queremos campos sempre editáveis (Input/Textarea always visible) com auto-save via debounce. Padrão diferente: usar Input/Textarea diretamente + useAutoSave, não EditableText.

CopyButton — esqueleto:

'use client'

import { useState, useCallback } from 'react'
import { Check, Copy } from 'lucide-react'

import { Button } from '@/components/ui/button'

interface CopyButtonProps {
  text: string
  label?: string
}

export function CopyButton({ text, label = 'texto' }: CopyButtonProps) {
  const [copied, setCopied] = useState(false)

  const handleCopy = useCallback(async () => {
    try {
      await navigator.clipboard.writeText(text)
      setCopied(true)
      setTimeout(() => setCopied(false), 2000)
    } catch {
      // Silently fail — clipboard API may not be available
    }
  }, [text])

  return (
    <Button
      variant="ghost"
      size="icon-sm"
      onClick={handleCopy}
      aria-label={copied ? 'Copiado' : `Copiar ${label}`}
    >
      {copied ? (
        <Check className="size-4 text-green-500" />
      ) : (
        <Copy className="size-4 text-muted-foreground" />
      )}
    </Button>
  )
}

parseHashtags — implementação:

export function parseHashtags(text: string): string[] {
  const raw = text.split(/[\s,]+/).filter(Boolean)
  const withHash = raw.map(s => (s.startsWith('#') ? s : `#${s}`))
  // Deduplicar case-insensitive, manter primeiro
  const seen = new Set<string>()
  return withHash.filter(h => {
    const lower = h.toLowerCase()
    if (seen.has(lower)) return false
    seen.add(lower)
    return true
  })
}

SocialPostEditor — esqueleto:

'use client'

import { useMemo, useState } from 'react'

import { Input } from '@/components/ui/input'
import { Textarea } from '@/components/ui/textarea'
import { SaveStatusIndicator } from '@/components/settings/save-status-indicator'
import { CopyButton } from './copy-button'
import { useAutoSave } from '@/hooks/use-auto-save'
import { parseHashtags } from './parse-hashtags'
import type { SocialPost } from '@/types/social'

interface SocialPostEditorProps {
  videoId: string
  networkId: string
  post: SocialPost
  onPostUpdated: (post: SocialPost) => void
}

export function SocialPostEditor({ videoId, networkId, post, onPostUpdated }: SocialPostEditorProps) {
  const [editCta, setEditCta] = useState(post.cta)
  const [editBody, setEditBody] = useState(post.body)
  const [editHashtags, setEditHashtags] = useState(post.hashtags.join(' '))

  const combinedValue = useMemo(() => ({
    cta: editCta,
    body: editBody,
    hashtags: parseHashtags(editHashtags),
  }), [editCta, editBody, editHashtags])

  const { saveStatus } = useAutoSave(
    combinedValue,
    async (value) => {
      const response = await fetch(
        `/api/videos/${videoId}/social-posts/${networkId}`,
        {
          method: 'PUT',
          headers: { 'Content-Type': 'application/json' },
          body: JSON.stringify(value),
        }
      )
      if (!response.ok) {
        const err = await response.json().catch(() => ({}))
        throw new Error(err.error?.message || 'Erro ao salvar post')
      }
      onPostUpdated({ ...post, ...value, processedBy: 'manual' })
    },
    1500
  )

  const hashtagsText = useMemo(
    () => parseHashtags(editHashtags).join(' '),
    [editHashtags]
  )

  return (
    <div className="space-y-4">
      {/* CTA */}
      <div className="space-y-1">
        <div className="flex items-center gap-2">
          <Input
            value={editCta}
            onChange={(e) => setEditCta(e.target.value)}
            className="font-medium"
            placeholder="Call to Action"
          />
          <CopyButton text={editCta} label="CTA" />
        </div>
      </div>

      {/* Body */}
      <div className="space-y-1">
        <div className="flex items-start gap-2">
          <Textarea
            value={editBody}
            onChange={(e) => setEditBody(e.target.value)}
            className="min-h-[120px] resize-none"
            placeholder="Corpo do post"
          />
          <CopyButton text={editBody} label="corpo" />
        </div>
      </div>

      {/* Hashtags */}
      <div className="space-y-1">
        <div className="flex items-start gap-2">
          <Textarea
            value={editHashtags}
            onChange={(e) => setEditHashtags(e.target.value)}
            className="min-h-[60px] resize-none text-sm text-muted-foreground"
            placeholder="#hashtag1 #hashtag2"
          />
          <CopyButton text={hashtagsText} label="hashtags" />
        </div>
      </div>

      <SaveStatusIndicator status={saveStatus} />
    </div>
  )
}

      <div className="space-y-3 border border-border rounded-md p-3">
        <Textarea
          value={additionalContext}
          onChange={(e) => setAdditionalContext(e.target.value)}
          maxLength={500}
          className="min-h-[80px] resize-none"
          placeholder="Ex: Foque mais no convidado principal..."
        />
        <div className="flex items-center gap-2">
          <Button size="sm" onClick={handleReprocess}>
            <RefreshCw className="size-4 mr-2" />
            Gerar novamente
          </Button>
          <Button size="sm" variant="ghost" onClick={() => setShowReprocessForm(false)}>
            Cancelar
          </Button>
        </div>
      </div>
    ) : (
      <Button variant="outline" size="sm" onClick={() => setShowReprocessForm(true)}>
        <RefreshCw className="size-4 mr-2" />
        Reprocessar
      </Button>
    )}
  </div>
)}

Decisão: Campos sempre visíveis vs click-to-edit

O componente EditableText existente usa click-to-edit (display → input → display). Para o SocialPostEditor, os campos devem ser sempre editáveis (Input/Textarea sempre visíveis), porque:

  1. O produtor vai editar frequentemente — click-to-edit adiciona fricção
  2. Auto-save com useAutoSave funciona melhor com controlled inputs permanentes
  3. Os 3 campos salvam juntos (um único PUT) — se um campo está em modo display, editar outro exigiria lógica complicada

Decisão: saveStatus único vs por campo

Usar um único useAutoSave com combinedValue (objeto com os 3 campos). Vantagens:

  • Um único PUT salva tudo (economiza requests)
  • Um único SaveStatusIndicator (UI mais limpa)
  • Deep comparison via JSON.stringify detecta mudanças em qualquer campo

Post prop sync

Quando o post é atualizado externamente (e.g., via reprocessamento LLM), os state locais (editCta, editBody, editHashtags) precisam ser sincronizados. Usar useEffect com dependência em post:

useEffect(() => {
  setEditCta(post.cta)
  setEditBody(post.body)
  setEditHashtags(post.hashtags.join(' '))
}, [post.cta, post.body, post.hashtags])

Nota: Isso pode causar re-render e resetar o timer do useAutoSave. Isso é desejável — após reprocessamento, o timer reseta e o lastSavedValueRef do hook será atualizado pelo isFirstRender skip.
