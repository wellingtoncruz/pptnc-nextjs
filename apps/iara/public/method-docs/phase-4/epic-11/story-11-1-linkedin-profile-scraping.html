Story 11.1: LinkedIn Profile Scraping para Co-host e Convidados

Status: done

Story

As a produtor de conteúdo, I want que os dados dos convidados sejam enriquecidos automaticamente a partir do LinkedIn, so that eu não precise preencher manualmente nome, cargo e empresa.

Acceptance Criteria

  1. AC1 - Scraping disparado após salvar contexto: Given o Wizard na Fase 0/1 com vídeo tipo episode, When o produtor preenche o campo LinkedIn de um co-host ou convidado e salva o contexto, Then uma chamada server-side fire-and-forget é feita para a BrightData API com a URL informada, e o produtor vê apenas o spinner normal do save (sem UI adicional).

  2. AC2 - Persistência na subcollection guests: Given a BrightData API retorna dados do perfil, When o scraping completa com sucesso, Then o JSON completo retornado é persistido em /podcasts/{podcastId}/guests/{docId}, o avatar é baixado e salvo em public/guests/{hash}.jpg, e o campo guests[i].photo do vídeo é atualizado com o path relativo /guests/{hash}.jpg.

  3. AC3 - Guest já existente (idempotência): Given um guest já existente na subcollection (mesmo campo url), When o scraping é disparado novamente, Then o documento é atualizado (não duplicado) e a imagem do avatar é atualizada se mudou.

  4. AC4 - Erro na BrightData API: Given a BrightData API retorna erro ou timeout, When o autosave do campo LinkedIn completa, Then a URL do LinkedIn é salva normalmente no vídeo, o erro é logado via structured logging, e o fluxo do produtor NÃO é bloqueado.

  5. AC5 - Apenas episódios: Given um vídeo do tipo cut ou reel, When o contexto é salvo, Then o scraping NÃO é disparado (apenas episode dispara scraping).

Dev Notes

Fluxo Completo

1. Produtor abre Wizard → Fase 0 (contexto) → preenche LinkedIn dos guests
2. Clica "Salvar" → PUT /api/videos/{videoId}/context (salva normalmente)
3. Após sucesso: client dispara POST /api/guests/scrape { videoId } (fire-and-forget)
4. Route Handler:
   a. Busca vídeo no Firestore
   b. Filtra guests com campo linkedin preenchido
   c. Para cada guest:
      - Chama BrightData API com linkedin URL
      - Se sucesso: upsert na subcollection guests
      - Se avatar URL: baixa imagem, salva em public/guests/{md5}.jpg
      - Atualiza guests[i].photo no vídeo com path /guests/{md5}.jpg
   d. Retorna contagem (irrelevante para o client — fire-and-forget)
5. Produtor NÃO vê feedback — se atualizar a página depois, verá o avatar

BrightData API — Comportamento

Endpoint: POST https://api.brightdata.com/datasets/v3/scrape?dataset_id=gd_l1viktl72bvl7bjuj0&notify=false&include_errors=true

Resposta HTTP 200 (sucesso síncrono, <60s):

[
  {
    "name": "Richard Branson",
    "url": "https://www.linkedin.com/in/richardbranson",
    "avatar": "https://media.licdn.com/...",
    "position": "Founder at Virgin Group",
    "current_company_name": "Virgin Group",
    "about": "...",
    "city": "London",
    "country_code": "GB",
    "linkedin_id": "...",
    ...
  }
]

Resposta HTTP 202 (timeout >60s): Retorna snapshot_id para polling. Decisão: NÃO implementar polling — se receber 202, logar warning e retornar null. O scraping ocorrerá na próxima vez que o produtor salvar o contexto.

Parâmetros:

  • notify=false: sem webhook callback
  • include_errors=true: inclui registros de erro para URLs que falharam

Match de guest: video.guests[i].linkedin === response[0].url

Avatar — Salvar em Disco (public/guests/)

Decisão: salvar imagem no filesystem em public/guests/.

  • O disco persistente já está mapeado no Cloud Run para public/guests/
  • Nomeação por hash MD5 da URL do LinkedIn: md5(linkedinUrl).jpg
    • Ex: URL https://linkedin.com/in/richard → arquivo public/guests/a1b2c3d4e5f6.jpg
  • O campo guests[i].photo no vídeo contém o path relativo: /guests/a1b2c3d4e5f6.jpg
  • A imagem é servida diretamente pelo Next.js como static asset
  • Hash garante idempotência (mesmo LinkedIn URL → mesmo arquivo → sobrescreve se atualizado)

Implementação do download:

import { createHash } from 'crypto'
import { writeFile, mkdir } from 'fs/promises'
import path from 'path'

async function downloadAndSaveAvatar(avatarUrl: string, linkedinUrl: string): Promise<string | null> {
  const hash = createHash('md5').update(linkedinUrl).digest('hex')
  const filename = `${hash}.jpg`
  const dirPath = path.join(process.cwd(), 'public', 'guests')
  const filePath = path.join(dirPath, filename)

  const response = await fetch(avatarUrl)
  if (!response.ok) return null

  const buffer = Buffer.from(await response.arrayBuffer())
  if (buffer.length < 1000) return null // placeholder image

  await mkdir(dirPath, { recursive: true })
  await writeFile(filePath, buffer)

  return `/guests/${filename}` // path relativo para o campo photo
}

Campo photo no VideoUpdateSchema

O campo guests[i].photo já é z.string().optional() no GuestSchema. Aceita qualquer string, incluindo paths relativos como /guests/a1b2c3.jpg. Nenhuma mudança no schema de video é necessária.

NÃO Sobrescrever Campos Manuais

Quando o scraping preenche dados, o Route Handler DEVE:

  • Atualizar APENAS guests[i].photo no vídeo (avatar baixado)

Descoberta: updateVideoAdmin valida com Zod

updateVideoAdmin() chama VideoUpdateSchema.parse(data) ANTES de persistir. O campo guests é z.array(GuestSchema).optional() no VideoUpdateSchema. Para atualizar apenas guests[i].photo, é necessário passar o array inteiro de guests (não é possível atualizar um item individual do array via Firestore).

Fluxo para atualizar photo:

  1. Buscar vídeo atual: getVideoAdmin(podcastId, videoId)
  2. Modificar video.guests[i].photo no array
  3. Salvar array inteiro: updateVideoAdmin(podcastId, videoId, { guests: updatedGuests })

Bug Fix Recente: Timestamp.now() vs FieldValue.serverTimestamp()

Na Story 11-2, descobrimos que FieldValue.serverTimestamp() falha a validação Zod em updateVideoAdmin(). A solução é usar Timestamp.now() para campos que passam por Zod, e FieldValue.serverTimestamp() é adicionado automaticamente para updatedAt. Seguir o mesmo padrão aqui.
