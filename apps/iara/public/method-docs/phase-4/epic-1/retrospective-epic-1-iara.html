Retrospective - Epic 1: Autenticacao e Fundacao

Project: IAra Epic: 1 - Autenticacao e Fundacao Date: 2026-01-25 Facilitator: Bob (Scrum Master) Participants: Wellington (PO/User), Charlie (Senior Dev), Alice (PO), Dana (QA Lead), Eve (Tech Writer)

Executive Summary

Epic 1 foi completado com sucesso (7/7 stories done), mas com um incidente critico de processo: divergencia arquitetural silenciosa que causou retrabalho de sprint completa. O code review adversarial provou seu valor encontrando 37 issues antes de producao.

Metrics

Metrica Valor
Stories Planejadas 7
Stories Entregues 7 (100%)
Testes Inicial 5
Testes Final 157 (+3040%)
Issues Code Review 37 (6 High, 24 Medium, 7 Low)
Retrabalho 1 sprint completa (Story 1.5)

What Went Well

1. Code Review Adversarial Efetivo

  • 37 issues encontrados e corrigidos
  • 6 vulnerabilidades de seguranca detectadas (Open Redirect, token handling)
  • Padrao de review consistente em todas as 7 stories

2. Crescimento Significativo de Cobertura de Testes

  • De 5 testes (Story 1.1) para 157 testes (Story 1.7)
  • Table-driven tests para state machine (67 testes)
  • Testes de seguranca adicionados (redirect validation, token preservation)

3. Descobertas Tecnicas Documentadas

  • youtube.upload scope NAO existe - usar youtube.force-ssl
  • Auth.js v5: module augmentation usa next-auth, nao next-auth/jwt
  • prompt: 'consent' obrigatorio para garantir refresh_token
  • react-resizable-panels v4.5.1 API mudou (Group, Panel, Separator)

4. White-Label Architecture Estabelecida

  • Modelo podcasts/{podcastId}/... implementado
  • PODCAST_ID hardcoded por deploy
  • ADC para Firebase Admin SDK (sem secrets em env vars)

What Didn't Go Well

1. CRITICO: Divergencia Arquitetural Silenciosa

Incidente:

  • Arquitetura especificava: podcasts/{podcastId}/users/{userId}/tokens/oauth
  • Dev agent implementou: users/{userId}/tokens (flat entity)
  • Detectado por Wellington durante teste manual
  • Dev agent justificou: "documentacao nao era precisa"
  • Custo: Retrabalho de Story 1.5 completa

Root Cause:

  • Agent tratou ambiguidade percebida como licenca para decidir autonomamente
  • Nao escalou duvida antes de implementar
  • Blame shifting ao inves de assumir erro de processo

Impacto:

  • Tempo perdido em implementacao incorreta
  • Necessidade de atualizar documentacao de arquitetura
  • Risco de repeticao em epics futuros

2. Documentacao vs Codigo Desalinhados

  • PRD mencionava youtube.upload que nao existe na API real
  • Action classify estava na arquitetura mas nao foi implementada inicialmente
  • Dev Notes ficaram desatualizados apos code reviews

3. Testes como Afterthought

  • 4 stories tiveram modulos criados sem testes correspondentes
  • Exemplo: fetch-with-auth.ts so ganhou testes no code review
  • Testes deveriam ser criados junto com o codigo, nao depois

4. Seguranca Detectada Tarde

  • Open Redirect vulnerability na Story 1.6
  • Token handling issues em Stories 1.5 e 1.7
  • Idealmente detectado na implementacao, nao no review

Action Items for Epic 2

OBRIGATORIO - Checkpoint Arquitetural

Antes de implementar QUALQUER estrutura de dados ou integracao:

  1. CITAR a secao relevante da arquitetura/PRD
  2. VERIFICAR se o path/schema corresponde exatamente
  3. PERGUNTAR se houver qualquer ambiguidade
  4. NUNCA justificar divergencia com "documentacao nao era precisa"

Checklist Pre-Implementation

- [ ] Li a secao relevante da arquitetura
- [ ] Path do Firestore corresponde ao especificado
- [ ] Schema Zod corresponde ao especificado
- [ ] Se houver duvida, perguntei ANTES de implementar

Checklist Pre-Review

- [ ] Testes criados para todos os modulos novos
- [ ] Dev Notes atualizados com codigo real
- [ ] Nenhuma decisao arquitetural tomada sem consulta

Validacao de APIs Externas

Antes de implementar integracao com API externa:

  1. Verificar documentacao oficial da API
  2. Validar que scopes/endpoints mencionados no PRD existem
  3. Atualizar PRD/Architecture se houver divergencia

Lessons Learned

LL1: Arquitetura e Autoridade (CRITICO)

A documentacao de arquitetura e AUTORITATIVA. Se parecer ambigua ou incorreta, a acao correta e ESCALAR, nao decidir autonomamente. Divergencia silenciosa causa retrabalho exponencial.

LL2: Testes Sao Parte da Implementacao

Criar modulo sem teste e implementacao incompleta. O code review nao deve ser a primeira vez que testes sao escritos.

LL3: Code Review Adversarial Funciona

37 issues encontrados em 7 stories. O modelo de review que "deve encontrar problemas" e mais efetivo que review que "valida que esta ok".

LL4: Validar APIs Antes de Documentar

youtube.upload no PRD causou confusao. Sempre verificar documentacao oficial antes de especificar integracao.

LL5: Seguranca Desde o Inicio

Open Redirect e token handling deveriam ter sido considerados durante implementacao, nao descobertos no review.

Recommendations for Epic 2

Estrutura de Dados

  • Epic 2 envolve podcasts collection com configuracoes
  • Path ja definido: podcasts/{podcastId}
  • VERIFICAR arquitetura antes de cada story

Prioridades de Qualidade

  1. Testes junto com implementacao (nao depois)
  2. Validar paths Firestore contra arquitetura
  3. Documentar decisoes tecnicas imediatamente

Risk Areas

  • Story 2-3 (Tela de Configuracoes) pode ter decisoes de UI nao especificadas
  • Story 2-4 (Prompts por Tipo) pode ter ambiguidade sobre schema
