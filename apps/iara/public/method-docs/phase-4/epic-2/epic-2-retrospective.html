Retrospective - Epic 2: Configuracao de Podcast

Project: IAra Epic: 2 - Configuracao de Podcast Date: 2026-01-26 Facilitator: Bob (Scrum Master) Participants: Wellington (PO/User), Charlie (Senior Dev), Dana (QA Lead)

Executive Summary

Epic 2 foi completado tecnicamente (5/5 stories done, 287 testes), mas a retrospectiva identificou um padrao recorrente critico: o agente fazendo suposicoes autonomas em vez de escalar duvidas. Este mesmo problema ocorreu no Epic 1 e se repetiu no Epic 2, resultando em retrabalho. Uma nova enforcement rule (#16) foi adicionada ao project-context para prevenir recorrencia.

Adicionalmente, foram identificadas divergencias significativas entre a especificacao e a implementacao de prompts, resultando na criacao da Story 2.6 para correcoes antes do Epic 3.

What Went Well

1. Autenticacao IAM/GCP Transparente

  • ADC (Application Default Credentials) funcionou sem friccao
  • Scripts de migracao conectaram ao Firestore sem configuracao adicional
  • Zero secrets em variaveis de ambiente
  • Decisao arquitetural do Epic 1 pagou dividendos

2. Migracao de Dados Robusta

  • 2293 documentos principais migrados
  • 8510 chunks de subcollections migrados
  • Script idempotente (pode ser executado multiplas vezes)
  • Relatorio estruturado de migracao

3. Code Review Adversarial

  • Encontrou issues reais em todas as stories
  • Auto-save salvando constantemente → fix com JSON.stringify
  • Unidades de tempo incorretas → padronizado em segundos
  • Next.js 16 middleware deprecation → migrado para proxy.ts

4. Cobertura de Testes

  • 287 testes ao final do epic
  • Testes co-localizados com arquivos fonte
  • Fake timers para hooks de auto-save

What Didn't Go Well

1. CRITICO: Agente Assumindo Sem Perguntar (RECORRENTE)

Epic 1:

  • Arquitetura especificava: podcasts/{podcastId}/users/{userId}/tokens/oauth
  • Agente implementou: users/{userId}/tokens (diferente)
  • Justificativa: "documentacao nao era precisa"
  • Custo: Retrabalho de Story 1.5 completa

Epic 2:

  • Documentacao nao especificava unidade de tempo
  • Agente assumiu minutos em vez de segundos
  • Descoberto no code review
  • Custo: Refatoracao de UI e testes

Nesta Retrospectiva:

  • Workflow especificava interacao com usuario
  • Agente gerou documento sozinho sem perguntar
  • Descoberto pelo usuario

Root Cause: Agente trata ambiguidade como licenca para decidir autonomamente, em vez de escalar a duvida.

2. Divergencia Arquitetural de Prompts

Especificado: Multiplos prompts por tipo de video

  • Episode: critica, edicao, compliance, titulos, descricao, tags
  • Cut: titulo, thumbs, descricao, tags
  • Reel: titulo, descricao, tags
  • Cada prompt com: description + expectedOutput

Implementado: 1 prompt generico por tipo

prompts: { episode: string, cut: string, reel: string }

Ausente: Personas (critic, writer) com role, objective, resume

Custo: Story 2.6 criada para correcoes

3. Bug de Autenticacao (RESOLVIDO)

Problema Original: Login/logoff cria novo usuario ao inves de atualizar existente

Root Cause Descoberto: O token.sub do Auth.js v5 (sem database adapter) e um UUID gerado pelo framework que muda a cada sessao - NAO e o Google User ID.

Solucao Final: Usar account.providerAccountId (Google User ID estavel) como identificador do usuario, nao token.sub.

Correcao em src/lib/auth.ts:

// ANTES (bugado):
const userId = token.sub // UUID que muda a cada login

// DEPOIS (correto):
const userId = account.providerAccountId // Google ID - imutavel

Lessons Learned

LL1: Enforcement Rules Sao Criticas (REFORCO)

Action items de retrospectiva NAO sao suficientes. Se o comportamento deve ser obrigatorio, DEVE estar nas enforcement rules do project-context. O agente le as rules a cada sessao.

LL2: Perguntar NAO e Fraqueza

Escalar duvidas antes de implementar NAO e sinal de incompetencia. E o comportamento correto que previne retrabalho exponencial. Divergencia silenciosa causa mais dano que uma pergunta.

LL3: Retrospectivas Devem Ser Interativas

O workflow de retrospectiva especifica interacao com o usuario. Gerar documentos unilateralmente ignora insights valiosos e viola o proposito do processo.

LL4: Validar Especificacao vs Implementacao

Mesmo com stories detalhadas, divergencias acontecem. Code reviews devem verificar nao apenas qualidade do codigo, mas aderencia a especificacao.

LL5: Auth.js v5 token.sub NAO e Estavel Sem Adapter

Sem um database adapter, o Auth.js v5 gera UUIDs internos para token.sub a cada sessao. Para identificadores estaveis de usuarios externos (Google, etc), usar account.providerAccountId.
