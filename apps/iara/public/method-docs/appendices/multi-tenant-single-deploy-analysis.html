Análise: Multi-Tenant Single Deployment

Data: 2026-02-19 Status: Documentado para evolução futura Contexto: Discussão party-mode após Epic 13 (Hardening v2.2.0)

Motivação

Na fase de validação, o modelo atual (um deploy por podcast) funciona. Mas conforme o IAra escalar para mais clientes, não é viável fazer setup completo de infraestrutura (Cloud Run service, Cloud Build trigger, env vars, secrets) para cada novo tenant. A evolução natural é um único deployment atendendo múltiplos podcasts, onde o podcastId é resolvido pelo vínculo do usuário logado.

Modelo Atual (Single-Tenant)

Cloud Run Service A (PODCAST_ID=podcast-a) → Firestore podcasts/podcast-a/...
Cloud Run Service B (PODCAST_ID=podcast-b) → Firestore podcasts/podcast-b/...
  • PODCAST_ID é constante global definida via env var no startup
  • Cada Cloud Run service atende exatamente um podcast
  • 30 arquivos source importam PODCAST_ID from @/lib/firebase/config
  • 13 arquivos de teste referenciam PODCAST_ID
  • Logger inclui podcastId como campo estático
  • Startup validation faz fail-fast se PODCAST_ID está vazio

Modelo Alvo (Multi-Tenant)

Cloud Run Service Único → Firestore podcasts/{podcastId}/...
                          (podcastId vem da sessão do usuário)
  • podcastId resolvido por request a partir da sessão Auth.js
  • User model ganha campo podcastIds: string[] (ou podcastId: string)
  • JWT token carrega podcastId ativo
  • Cada API route extrai podcastId da session, não de constante global

Camadas de Impacto

1. Modelo de Dados: User → Podcast

Hoje: User tem role mas nenhum vínculo com podcast. O PODCAST_ID global assume que todo user pertence ao mesmo podcast.

Necessário:

  • Campo podcastIds: string[] no documento User (suporta multi-podcast futuro)
  • Ou podcastId: string se 1:1 for suficiente na primeira iteração
  • Seed/admin precisa associar users a podcasts

Decisão em aberto: Um usuário pode pertencer a vários podcasts?

  • Se sim → podcast selector na UI + conceito de "podcast ativo" na sessão
  • Se não → mais simples, podcastId vem direto do perfil

2. Session/JWT: podcastId por request

Hoje (src/lib/auth.ts):

  • JWT callback salva userId, role, accessToken, refreshToken
  • Session callback expõe user.id, user.role
  • PODCAST_ID é importado via await import('./firebase/config') na linha 81

Necessário:

  • JWT callback: resolver podcastId do user e gravar no token
  • Session callback: expor session.podcastId
  • Type augmentation: adicionar podcastId em Session e JWT
// Exemplo conceitual
interface Session {
  user: { id: string; role: 'admin' | 'user' }
  podcastId: string  // ← NOVO
  error?: '...'
}

Opções de resolução:

Opção Descrição Prós Contras
Session-based podcastId gravado no JWT no login Simples, sem overhead por request Requer re-login para trocar podcast
Header-based Frontend envia x-podcast-id Flexível para multi-podcast Middleware de validação necessário
URL-based /api/podcasts/{id}/videos/... RESTful Reescreve todas as rotas

Recomendação: Session-based na v1 (mais simples). Evoluir para header-based se multi-podcast por user for necessário.

Hoje: Cada route faz import { PODCAST_ID } from '@/lib/firebase/config' e usa diretamente.

Padrão de migração:

// ANTES (single-tenant)
import { PODCAST_ID } from '@/lib/firebase/config'

export async function GET() {
  const session = await requireAuth()
  const videos = await getVideos(PODCAST_ID)
}

// DEPOIS (multi-tenant)
export async function GET() {
  const { podcastId } = await requireAuth()  // podcastId vem da session
  const videos = await getVideos(podcastId)
}

Helper sugerido: requireAuth() já existe. Evoluir para retornar { session, podcastId }. Isso centraliza a extração num único ponto — cada route só precisa desestruturar.

4. Firestore Admin Functions

Hoje: Functions como getVideos(podcastId), updateVideo(podcastId, videoId, data) já recebem podcastId como parâmetro — o acoplamento está nas routes que passam a constante.

Impacto: Baixo nas functions, alto nas routes (caller side).

5. Logger: podcastId per-request

Hoje (src/lib/logger.ts):

import { PODCAST_ID } from '@/lib/firebase/config'
// podcastId é campo estático em todos os logs

Necessário: podcastId dinâmico por request.

Opções:

  • AsyncLocalStorage (Node.js): Middleware seta contexto no início de cada request, logger lê automaticamente. Zero mudança nos callers.
  • Parâmetro explícito: log('INFO', msg, { podcastId }) — mais verboso, mas sem magia.

Recomendação: AsyncLocalStorage. Next.js App Router já usa internamente. Criar src/lib/request-context.ts com middleware.

6. YouTube OAuth: Multi-Canal

Hoje: Tokens OAuth ficam no documento do User. O token dá acesso ao canal YouTube do usuário, não do podcast.

Cenário problemático: Se o mesmo admin gerencia vários podcasts com canais YouTube diferentes, os tokens OAuth precisam ser:

  • Separados por podcast/canal, OU
  • O admin faz login com a conta Google que tem acesso a cada canal

Complexidade: Alta se multi-canal for necessário. Pode ser adiado se na primeira iteração cada user opera apenas um canal.

7. UI: Podcast Selector

Necessário se multi-podcast por user:

  • Componente de seleção de podcast (sidebar ou header)
  • Estado "podcast ativo" no frontend
  • Refresh de dados ao trocar podcast

Pode ser adiado se 1 user = 1 podcast na primeira iteração.

8. Config.ts: Remoção do PODCAST_ID global

Hoje:

export const PODCAST_ID = process.env.PODCAST_ID || 'pptnc'
if (!PODCAST_ID) throw new Error('[CONFIG] PODCAST_ID is required but empty.')

Depois: PODCAST_ID deixa de existir como constante. Startup validation muda. Log de startup não tem mais "Tenant: X" fixo.

Estratégia de Migração Incremental (Recomendada)

Fase 0: Preparação (backwards-compatible)

  • Adicionar podcastIds: string[] ao schema User
  • Popular automaticamente no login (usar PODCAST_ID env var como fonte)
  • Zero breaking change — sistema continua funcionando igual

Fase 1: Dual-mode nas routes

  • Criar helper: getPodcastId(session) que:
    • Tenta extrair da session (multi-tenant mode)
    • Fallback para env var PODCAST_ID (single-tenant mode)
  • Migrar routes uma a uma para usar o helper
  • Backwards-compatible — deploys existentes continuam funcionando

Fase 2: Session como fonte primária

  • Auth.js grava podcastId no JWT/Session
  • Middleware valida que user pertence ao podcast
  • Logger via AsyncLocalStorage
  • Testar com 2+ podcasts no mesmo deploy

Fase 3: UI multi-podcast (se necessário)

  • Podcast selector para users com podcastIds.length > 1
  • Session switching sem re-login

Fase 4: Cleanup

  • Remover PODCAST_ID do config.ts
  • Remover fallback single-tenant
  • Atualizar docs e onboarding guide

Decisões em Aberto (para retomar no futuro)

  1. 1:1 vs N:N — Um user pertence a 1 ou N podcasts?
  2. YouTube tokens — Compartilhados ou por podcast?
  3. Firestore database — Todos os tenants no mesmo database ou separados?
  4. Billing/quotas — Limites de Vertex AI são por projeto. Multi-tenant num projeto = quota compartilhada.
  5. Isolamento de dados — Security rules por podcastId? Risco de cross-tenant leak?
  6. Admin global vs admin por podcast — Existe um super-admin que vê todos os podcasts?
